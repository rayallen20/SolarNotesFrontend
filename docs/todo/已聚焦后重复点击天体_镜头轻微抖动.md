# 已聚焦后重复点击天体导致镜头轻微抖动 — 修复方案(`requestFocus` 同天体守卫)

> 缘起:用户在 `focused` 状态下再次点击同一颗天体,镜头会发生**轻微移动**而不是预期的"无反应"。
>
> 根因是 `requestFocus` 没有"同天体短路"守卫:它会无条件把状态机推进到 `focusing`、置 `needsInit = true`,下一帧 `tickFocus` 跑 `initFocusAnimation`,**根据当前 `camera.position`(可能已被用户用 OrbitControls 微调过)重算"标准位姿"**,然后从当前位姿插值回这个新的标准位姿——视觉上就是几像素到几十像素的飘移。
>
> 修复:在 `src/stores/focus.js` 的 `requestFocus` 内,加一条 `phase !== idle && focusedEntity === anchor` 的早退守卫。把"在该天体的聚焦流程中(focusing / focused / clearing 任一),重复请求聚焦同一天体"统一识别为 no-op。

---

## 1. 根因详解

### 1.1 触发链

| 步骤 | 文件:行 | 行为 |
|---|---|---|
| 用户在 `focused` 状态下再次点击同一天体 X | `pages/SolarCanvas.vue:155` / `components/label/ContentLayer.vue:82` | 调 `focusStore.requestFocus(X)` |
| `requestFocus` 无条件推进状态机 | `stores/focus.js:94-104` | phase `focused → focusing`,`needsInit = true` |
| 下一帧 tick | `three/interaction/focus.js:219-235` | `needsInit` 为真 → 进入 `initFocusAnimation` |
| `initFocusAnimation` 重算 `to*` | `three/interaction/focus.js:120-170` | `from* = 当前 camera.position`,`to* = 基于当前 camera 朝向重算的标准位姿` |
| `advanceCameraLerp` 插值 | `three/interaction/focus.js:199-210` | 从当前位姿过渡到新的标准位姿 → **可见的镜头移动** |

### 1.2 为什么 `to*` 会变

`initFocusAnimation` 内的 `to*` 计算依赖**当前**的 `camera.position` 和 `camera.matrixWorld`:

```js
// focus.js:136
targetToCameraDirection.copy(camera.position).sub(targetPosition).normalize()

// focus.js:155
cameraRightWorld.setFromMatrixColumn(camera.matrixWorld, 0).normalize()
```

而 `focused` 状态下 `controls.enabled = true`(`focus.js:230`),用户可以用 OrbitControls 旋转 —— 只要旋转一点点:

- `targetToCameraDirection` 偏移 → `toCameraPosition` 落到新方向上 → 与当前位置不同
- `cameraRightWorld` 偏移 → `toControlsTarget` 跟着平移 → 与当前 `controls.target` 不同

两端都漂了一小段,插值出来的就是"轻微移动"。

---

## 2. 修复方案

### 2.1 守卫位置:`stores/focus.js` 的 `requestFocus`

`stores/focus.js:94`,在"anchor 非空"守卫的下方插入:

```js
function requestFocus(anchor) {
    if (anchor === null || anchor === undefined) {
        return
    }

    // 已经在该天体的聚焦流程中(focusing/focused/clearing均算): 静默no-op
    // - focusing/focused: 避免重算标准位姿造成镜头轻微抖动
    // - clearing: 让退出动画继续走完, 不取消
    if (phase.value !== FocusPhase.idle && focusedEntity.value === anchor) {
        return
    }

    animation.shouldCaptureHome = (phase.value === FocusPhase.idle)
    phase.value = FocusPhase.focusing
    focusedEntity.value = anchor
    animation.needsInit = true
}
```

### 2.2 守卫的两部分含义

```js
phase.value !== FocusPhase.idle && focusedEntity.value === anchor
```

| 子条件 | 语义 |
|---|---|
| `phase !== idle` | 当前状态机已经在聚焦流程中(focusing / focused / clearing 任一) |
| `focusedEntity === anchor` | 流程的目标就是这次点击的同一颗天体 |

两者同时成立 → 该请求**不会产生新的、有意义的聚焦动画**,直接 no-op。

> **关于 `phase !== idle` 这层的冗余**:`idle` 状态下 `focusedEntity` 为 null(在 `finishClear` 中被置空,`stores/focus.js:143-146`),与非 null 的 `anchor` 天然不相等。所以 `focusedEntity === anchor` 这一条已经天然排除了 idle 情形。**保留 `phase !== idle` 是为了让代码读起来直接表达"非 idle"语义**,而不是依靠"null vs Object3D 永不相等"这种隐式推理。

---

## 3. 守卫后的状态转移矩阵

| 当前状态 | `focusedEntity` | 点击天体 | 守卫成立? | 结果 |
|---|---|---|---|---|
| idle | null | X | 否(phase 是 idle) | 进入聚焦 X ✓ |
| focusing 到 X | X | X | **是** | **no-op**(顺手消掉"重复点击导致动画重启"的隐式 bug) |
| focusing 到 Y | Y | X | 否(Y ≠ X) | 切换换焦到 X ✓ |
| focused 于 X | X | X | **是** | **no-op**(用户报的 bug,本次修复目标) |
| focused 于 Y | Y | X | 否 | 切换换焦到 X ✓ |
| clearing(上一颗 X) | X | X | **是** | **no-op**,clear 继续走完 |
| clearing(上一颗 Y) | Y | X | 否 | 取消 clear,切到 focusing X(此时 `home*` 不被覆盖,符合预期) |

7 种状态全覆盖,无暗角。

---

## 4. 顺手消掉的隐式 bug:`focusing` 同天体重复点击

之前若动画进行到一半时再次点击同一天体,会:

1. `requestFocus(X)` 无条件把 `needsInit` 置为 `true`
2. 下一帧 `tickFocus` 跑 `initFocusAnimation`,**重置 `markAnimationStart` 的时间戳**
3. 等效于把动画进度条拨回 0,又走一遍完整的 600 ms 动画

用户视角:点了一下,以为没事,实际动画又长了 600 ms。本次守卫加上后该副作用一并消失。

---

## 5. 为什么不在 `initFocusAnimation` 里用"`from ≈ to` 就跳过"

考虑过的替代方案:在 `initFocusAnimation` 末尾检测算出来的 `to*` 与 `from*` 距离 < ε,直接 `settleFocused` 跳过动画。**不采用**,原因:

1. **仍然消耗一次状态机往返**:`needsInit → initFocusAnimation → markAnimationStart → settleFocused`,逻辑链拉长,没有"早退"的清爽
2. **ε 阈值难定**:旋转一点点产生的差值多大算"应该忽略"?这是个产品语义("用户点了一下,系统应该认为他想干嘛"),无法用阈值清晰表达
3. **错过 §4 的隐式 bug**:`focusing → 同天体重复点击` 这种"动画重启"的副作用,在 `initFocusAnimation` 层守卫并不能识别 —— 那一刻 `from ≠ to`(`from` 是当前中途位置,`to` 是终点),阈值守卫不会 fire,但用户其实希望"什么都不做"

**真正的产品语义是"已经在那儿了,别再来一次"**,这个语义在意图层(`requestFocus`)就能表达清楚,不需要下沉到几何计算层。

---

## 6. 为什么守卫放 store,不放调用方

聚焦的调用方目前有 2 处:

| 调用方 | 文件:行 |
|---|---|
| `SolarCanvas.vue` 的 click 回调 | `pages/SolarCanvas.vue:155` |
| `ContentLayer.vue` 的"聚焦按钮"回调 | `components/label/ContentLayer.vue:82` |

如果把守卫放调用方:

- 两处都要复制同样的判断
- 未来新增第三个调用方时容易漏写
- 把"应不应该触发聚焦动画"的决策权下放给 UI 层,违反"状态机的转移规则在状态机内部定义"

放在 `requestFocus` 内:

- 单点真理
- 所有调用方"无脑调用"即可,守卫由 store 兜底
- 与已有的"anchor 非空"守卫风格一致(`stores/focus.js:95-97`)

## 9. 风险与未尽事项

### 9.1 守卫名是否需要抽成谓词常量

当前守卫是 1 行内联条件 + 注释。若以后 `requestFocus` 继续累积更多守卫(例如"某些天体禁止聚焦"、"防抖"),可以考虑把每个守卫抽成谓词函数。但**本次只有一个新增,内联即可**,不预先抽象。

### 9.2 与 `isAlreadyTargeting` 风格命名变量的取舍

讨论过把守卫条件抽成命名变量:

```js
const isAlreadyTargeting = phase.value !== FocusPhase.idle && focusedEntity.value === anchor
if (isAlreadyTargeting) {
    return
}
```

最终选择**内联**,理由:

- 同文件内 `requestClear` 也使用内联条件(`stores/focus.js:110-112`),保持风格一致
- 单次使用、含义清晰,命名抽离反而**增加阅读跳转**

如果后续这个条件需要在 store 的其他 action / getter 中复用(例如做一个对外暴露的 `isFocusedOn(anchor)` 查询),再抽离不迟。
