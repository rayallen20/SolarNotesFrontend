# 俯视角度聚焦时天体偏离视口右侧 — 修复方案(钳制相机极角)

> 缘起:把相机拉到近乎垂直于黄道面(俯视看天体公转)时点击天体触发聚焦,**天体并没有出现在视口右侧,而是落在视口下方(有时左下、有时右下,随起始方位角而变)**。
>
> 根因是 OrbitControls 把 `camera.up` 锁死在 `(0, 1, 0)`,**末态相机靠近极点(垂直方向)时,其本地 +Y 轴会被显著"拉扁"到水平方向**——这是一类标准的 gimbal lock 不稳定。`controls.target` 在世界水平面上的偏移在这种姿态下不再是"纯屏幕水平"的偏移,会在屏幕 Y 上留下投影,表现为天体下沉。
>
> 修复:在 `initFocusAnimation` 计算完 `targetToCameraDirection` 之后,**钳制它的垂直分量** —— 等价于强制聚焦末态相机距离视场极点至少 ~20°。聚焦动画期间相机会平滑过渡到这个角度,代价是损失少量"俯视感",换取末态相机基矢量的稳定。

---

## 1. 根因详解

### 1.1 触发链

`initFocusAnimation` 内 `toControlsTarget` 的计算逻辑(`focus.js:150-163`)本身没错:

```js
camera.updateMatrixWorld()
cameraRightWorld.setFromMatrixColumn(camera.matrixWorld, 0).normalize()
// 沿"屏幕水平向右"的反方向偏移, 把天体推到屏幕右侧
targetOffset.copy(cameraRightWorld).multiplyScalar(-targetShift)
toControlsTarget.copy(targetPosition).add(targetOffset)
```

但 `controls.update()` 在动画末态计算相机本地基矢量时,使用的是 `camera.up = (0, 1, 0)`:

```js
// OrbitControls 内部, 简化为伪代码
z_end = (camera.position - controls.target).normalize()    // 后向
x_end = (camera.up × z_end).normalize()                    // 右
y_end = z_end × x_end                                       // 上(屏幕)
```

当相机近极点(`z_end ≈ camera.up`)时,**`y_end = up - (up·z_end)·z_end` 的水平分量会被显著放大**——天体相对 `controls.target` 的水平偏移会同时投影到 `x_end` 和 `y_end` 上。

### 1.2 具体数值(用户报 bug 的 case)

相机起始位置 `(0, 100, 5)`,天体在原点,`targetShift = 10`,`desireDistance ≈ 100`:

| 量 | 值 | 期望 vs 实际 |
|---|---|---|
| `cameraRightWorld`(start) | `(1, 0, 0)` | 屏幕水平向右,世界 +X 方向 ✓ |
| `toControlsTarget` | `(-10, 0, 0)` | 在天体世界 -X 方向 10 单位处 ✓ |
| `toCameraPosition` | `(0, 99.88, 4.99)` | 在天体正上方 ✓ |
| 末态 `x_end`(世界) | `(0.447, 0, -0.894)` | 期望 `(1, 0, 0)`,实际旋转了 63° |
| 末态 `y_end`(世界) | `(-0.889, 0.111, -0.444)` | 期望接近 `(0, 1, 0)`,实际**几乎水平** |
| 天体在相机本地坐标 | `(4.5, -8.9, -99.5)` | 期望 `(10, 0, -100)`,实际**屏幕右下** |

`-8.9` 的垂直分量正是用户看到的"天体跑到视口下方"。如果起始方位角不同(比如相机在 `(5, 100, 0)` 而不是 `(0, 100, 5)`),`y_end` 的水平分量符号会反过来,天体就跑到左下——这就是用户说的"有时左下、有时右下"。

### 1.3 数学根源(一句话)

`y_end = z_end × x_end` 在 `z_end ≈ up` 时取值不稳定。任何 `controls.target` 的水平偏移都会让 `y_end` 倾出水平面,把"水平偏移"映射到屏幕的 Y 轴上。

## 2. 修复方案

### 2.1 改动一:文件顶端常量段新增三个常量

`src/three/interaction/focus.js:8-27` 现有的"相机数学配置常量"段末尾,追加:

```js
/**
 * @type {Number} 聚焦相机距离视场极点(±Y轴)的最小角度(单位: 度).
 *      调小: 末态相机更接近俯视/仰视,但残余垂直偏移增大;
 *      调大: 末态相机更远离极点,俯视感损失更多.
 *      详细 trade-off 见 §3
 * */
const MIN_POLAR_OFFSET_DEG = 20

/**
 * @type {Number} 派生量: `targetToCameraDirection.y` 的绝对值上限 = cos(MIN_POLAR_OFFSET_DEG).
 *      超过此值时触发极角钳制
 * */
const MAX_Y_ABS = Math.cos(THREE.MathUtils.degToRad(MIN_POLAR_OFFSET_DEG))

/**
 * @type {Number} 派生量: 钳制后 `targetToCameraDirection` 在XZ平面内的投影长度 = sin(MIN_POLAR_OFFSET_DEG)
 * */
const MIN_XZ_LEN = Math.sin(THREE.MathUtils.degToRad(MIN_POLAR_OFFSET_DEG))
```

旋钮只有一个(`MIN_POLAR_OFFSET_DEG`),其他两个是它的派生量 —— 后续调参时只改这一个数,另外两个自动跟随。

> **命名分层**:配置层用**角度**(`MIN_POLAR_OFFSET_DEG`,以度为单位、唯一可调旋钮),数学层用**坐标轴/平面上的标量**(`MAX_Y_ABS` 是 Y 分量绝对值的上限,`MIN_XZ_LEN` 是 XZ 平面投影长度的下限)。两组分别说清自己的角色,不掺杂"距极点"这个间接概念;并且**避开了 `COMPONENT` 这个在 Vue/前端工程里默认指代"UI 组件"的歧义词**。
>
> **`MIN_` 而不是 `MAX_`** 的理由:`MIN_POLAR_OFFSET_DEG` 表达的是"末态相机**至少**距离极点这么多度",`if (Math.abs(.y) > MAX_Y_ABS)` 触发钳制时的语义不歧义。

### 2.2 改动二:`initFocusAnimation` 内插入钳制块

`src/three/interaction/focus.js:136`(`targetToCameraDirection.copy(...).normalize()` 这一行)**之后**,插入:

```js
// 计算从被聚焦天体指向相机的方向
targetToCameraDirection.copy(camera.position).sub(targetPosition).normalize()

// === 新增:钳制聚焦相机的极角,距离视场极点(±Y)至少 MIN_POLAR_OFFSET_DEG ===
// targetToCameraDirection.y 是该方向的垂直分量,= cos(polar);
// |.y| 越接近 1, 相机越靠近极点, OrbitControls 计算的相机本地基矢量越不稳定,
// 表现为聚焦末态天体偏离视口水平中线
if (Math.abs(targetToCameraDirection.y) > MAX_Y_ABS) {
    const verticalSign = Math.sign(targetToCameraDirection.y) || 1
    const horizontalLen = Math.hypot(targetToCameraDirection.x, targetToCameraDirection.z)

    if (horizontalLen < 1e-6) {
        // 相机正好在天体正上方/正下方, 无方位角可保留: 默认沿世界+X方向倾斜
        targetToCameraDirection.set(
            MIN_XZ_LEN,
            verticalSign * MAX_Y_ABS,
            0,
        )
    } else {
        // 保留原方位角(.x/.z 的相对比例), 仅缩放横向分量到新长度
        const scale = MIN_XZ_LEN / horizontalLen
        targetToCameraDirection.x *= scale
        targetToCameraDirection.z *= scale
        targetToCameraDirection.y = verticalSign * MAX_Y_ABS
    }
}
// === 钳制结束 ===
```

> `verticalSign || 1` 处理 `.y === 0` 的退化情况(理论上不会触发,因为 `Math.abs(.y) > MAX_Y_ABS` 已经排除了 `.y = 0`,但 `Math.sign(0) = 0` 仍需要兜底)。
>
> 函数体内**不再出现任何** `degToRad` / `cos` / `sin` 调用 —— 三个角度变换在模块加载时一次性算好,每次进入聚焦只做比较和赋值。

### 2.3 下游为何不需要改

钳制只动 `targetToCameraDirection`,**下游计算全部自动跟着改**:

| 下游 | 是否依赖 `targetToCameraDirection` | 自动跟随? |
|---|---|---|
| `cameraOffset` | `ttc × desireDistance`(`focus.js:147`) | ✓ |
| `toCameraPosition` | `body + cameraOffset` | ✓(末态相机自动落到钳制后的位置) |
| `cameraRightWorld` | 读 `camera.matrixWorld`(start)的第 0 列 | **不依赖 ttc**,继续用 start 朝向算 |
| `targetOffset` / `toControlsTarget` | 用 `cameraRightWorld` 和 `targetShift` | 与 ttc 无关 |

`cameraRightWorld` 继续用 start 矩阵这件事是**有意保留**的:钳制的目标是让**末态相机姿态远离极点**,而不是改"屏幕水平方向"的世界含义。start 那一刻 `cameraRightWorld` 已经准确表达了"屏幕水平向右"在世界中的指向,沿这个方向偏移 `controls.target` 仍然正确。

### 2.4 `home*` 的捕获不被破坏

`home*` 在钳制之前的位置捕获:

```js
// focus.js:130-133, 在钳制之前
if (store.animation.shouldCaptureHome) {
    homeCameraPosition.copy(camera.position)
    homeControlsTarget.copy(controls.target)
}
```

所以 `home*` 仍然保留的是用户进入聚焦**之前**的原始视角(可能是近俯视)。退出聚焦时相机正确回到这个原始视角——钳制只影响聚焦末态,不影响"退出后回到哪里"。

## 3. 钳制值选择的 trade-off

`MIN_POLAR_OFFSET_DEG` 越大,末态相机离极点越远 → 残余偏移越小 → 但**用户的俯视感损失越大**。

下表是相机起始几乎正上方(原始俯视)时,各钳制值的末态表现(同一组 D / fovX / targetShift):

| `MIN_POLAR_OFFSET_DEG` | 末态距极点 | 末态相机俯视感 | 残余垂直偏移(占屏高) |
|---|---|---|---|
| 15 | 距极 15°(elevation 75°) | 仍非常俯视 | ~3.4% |
| **20** | **距极 20°(elevation 70°)** | **偏俯视** | **~2.5%** |
| 25 | 距极 25°(elevation 65°) | 中等俯视 | ~2.0% |
| 30 | 距极 30°(elevation 60°) | 明显侧视感 | ~1.7% |

900 px 高的视口下,2.5% ≈ 22 px ——目测基本贴齐"水平中线"。我推荐 **20** 作为出厂值,理由:

- 残余偏移肉眼几乎不可察
- 仍保留大部分俯视感——用户从近乎垂直拉过来,聚焦后看起来还是从较高角度看,只是不再完全顶视
- 离 OrbitControls 默认的 `maxPolarAngle = Math.PI` / `minPolarAngle = 0` 有充足缓冲,**不会和用户自由浏览时的极角操作冲突**(用户仍可以拖到完全俯视;只是触发聚焦那一刻,相机会平滑过渡到 20° 偏离极点的姿态)

如果觉得 2.5% 还是能看出来,把 `MIN_POLAR_OFFSET_DEG` 收紧到 25 或 30 即可——**只改这一个数,`MAX_Y_ABS` 和 `MIN_XZ_LEN` 会在模块加载时按新值重新派生**。

## 4. 为什么残余偏移消不掉

数学上,只要满足下面三个前提,残余偏移就**必然存在**:

1. `camera.up` 固定为 `(0, 1, 0)`
2. `controls.target` 与 `body` 在世界水平面上有偏移(就是我们的 `targetShift` 偏移)
3. 相机不在"赤道"(elevation ≠ 0)

末态 `y_end = (up - (up·z_end)·z_end).normalize()` 总会含有水平分量,而 `controls.target` 的水平偏移会有一部分投到这个水平分量上,从而在屏幕 Y 上留下投影。

想严格归零有两个方向,都不是好交易:

- **解非线性方程**(令 `(body - toCameraPosition) · y_end = 0`):该方程在近极点附近迭代不收敛,实测会震荡
- **聚焦期间临时换 `camera.up`**(沿某个"看起来更稳"的方向):退出聚焦时 OrbitControls 的 up 切回 `(0, 1, 0)` 会产生可见跳变

钳制极角是性价比最高的折中——用极小的视角约束换取末态相机基矢量稳定。

## 7. 风险与未尽事项

### 7.1 钳制使聚焦动画感观"多走一段"

近俯视的用户点击天体后,会看到相机**平滑下沉到约 20° 极角偏离**的位置,而不是"原地稍微平移"。这是钳制的设计意图,不是 bug。如果发现这个过渡感觉过于剧烈,可以:

- 收紧钳制到 15°(更接近原视角,但残余偏移变大)
- 或者在退出聚焦时也启用"home 回到钳制后的位置而不是原始位置",让用户视角不再回弹——但**不推荐**,这会让用户的"回到原视角"预期落空

### 7.2 OrbitControls 的 `minPolarAngle` / `maxPolarAngle` 与本钳制的关系

OrbitControls 自身支持 `minPolarAngle` / `maxPolarAngle` 来限制自由浏览时的极角。本次钳制**只作用于聚焦动画末态**,不限制自由浏览。两者职责不同:

| 限制 | 作用域 | 目的 |
|---|---|---|
| OrbitControls `min/maxPolarAngle` | 自由浏览全程 | 防止用户翻越极点导致镜头翻转 |
| 本次 `MIN_POLAR_OFFSET_DEG` | 仅聚焦动画末态 | 避开 `controls.update()` 的 gimbal lock 数值不稳定 |

如果你将来想给 OrbitControls 也加 polar 限制,把两边的常量名错开命名,避免读者混淆。

### 7.3 数学层面的备选方案备忘

§4 提到的两条"理论上能严格归零"的路径,这里再正式记一笔,**本次不采用**但留作未来参考:

1. **数值迭代求解 `(body - toCameraPosition) · y_end = 0`** —— 经实测,近极点附近会震荡。如果未来要做必须严格归零的场景(例如截图/分享 API),可以考虑加阻尼或限制迭代次数后回退到钳制
2. **聚焦期间用临时 `up`** —— 沿当前 ttc 方向构造一个与之正交的临时 up,聚焦末态把 up 切回 `(0,1,0)`。问题是切回那一刻会产生明显的镜头翻转,需要再做一段"up 重对齐"的次级动画,工程复杂度显著上升
