# `calcProjection` 屏幕投影半径计算偏差

> 缘起:`src/three/lib/projection.js` 中 `calcProjection()` 函数最后一行,`radiusPx = Math.hypot(deltaX, deltaY) / 2` 末尾的这个 `/ 2` 是一个没有数学依据的 magic number。当时用 AI 给出的原始实现是 `Math.hypot(deltaX, deltaY)`(没有 /2),但实测发现没有 /2 时 hover 检测会偏大,/2 之后凑合可用。本 TODO 记录这件事的真正成因和后续修复方案,等"投射检测 + 悬停状态机 + label 显示"主流程跑通之后再回来处理。

---

## 1. 问题起源

### 1.1 算法本身没问题

`calcProjection()` 用的是 perspective camera 下计算球体屏幕投影半径的**标准右采样法**,三步走:

1. 把球心 `centerWorld` 投影到屏幕,得到 `(centerX, centerY)`
2. 在世界坐标里从球心沿"相机右"方向延伸 1 个世界半径,得到采样点 `cameraRightSampleWorld`,把它也投影到屏幕,得到 `(edgeX, edgeY)`
3. 两个屏幕点的像素距离 ≈ 球的屏幕半径

数学推导:

- 采样点 E = C + R̂ · radiusWorld(R̂ 是相机右单位向量,垂直于观察方向)
- 因为 R̂ ⊥ 观察方向,**E 和 C 的相机深度近似相等**
- 在 perspective camera 下,同深度两点的屏幕距离 ∝ (世界距离 / 深度)
- 所以 `|E_screen - C_screen|` ≈ 球的屏幕半径

这是一个近似(真正的轮廓边来自切线圆锥,球心偏离光轴时会略大),但典型场景下误差在 1% 以内,够用。

**结论:`Math.hypot(deltaX, deltaY)` 本身就是屏幕半径,数学上不需要再 /2。**

### 1.2 那 /2 凭什么"实测有效"?

最可能的原因是:**当时拿到的 `radiusWorld` 比真实可见轮廓的半径大了差不多一倍**。`/2` 是经验补偿,不是原理修正。

具体到这份代码,有一条很可疑的路径——`getLocalBoundingSphere()` 的非 Mesh 分支(原项目从 `universeBlog/src/lib/projection.js` 照抄过来的部分):

```js
// projection.js getLocalBoundingSphere() 非 Mesh 分支
box.setFromObject(object)         // 世界 AABB
box.getBoundingSphere(sphere)     // ← 这里
```

`Box3.getBoundingSphere(target)` 在 Three.js 内部的实现是:

```js
// three/src/math/Box3.js
target.radius = this.getSize(_vector).length() * 0.5   // 对角线的一半
```

这是**外接球**(过 AABB 8 个角的球),不是物体的可见轮廓:

| 物体形状 | AABB | 外接球半径 | 可见半径 | 比值 |
|---|---|---|---|---|
| 边长 L 的立方体 | L×L×L | L·√3/2 ≈ 0.866L | L/2(内接) | **1.73x** |
| 直径 D 的球(模型紧贴 AABB) | D×D×D | D·√3/2 ≈ 0.866D | D/2 | **1.73x** |

也就是说,**只要传给 `calcProjection` 的 `object` 走了非 Mesh 分支,`radiusWorld` 就会比真实可见半径大约 1.73 倍**。

`/2` 把它压回到 `1.73 / 2 ≈ 0.866` 倍真实半径——略微偏小,但 hover 行为"看起来对"。1.73 ≠ 2,所以这只是凑合。

### 1.3 为什么这个偏差在原项目里也没暴露

原项目里 hover 检测主要靠 raycaster 命中具体 mesh,屏幕投影半径只用作"sticky 阶段进入/退出阈值"和"label 显示靠近度"判定的参考量,精度容忍度比较高,差个 10-20% 不会让交互行为明显出错,所以 magic number 一直没被发现。

### 1.4 为什么"调用方传 root group"会触发非 Mesh 分支

现状的悬停状态机里,`activeEntity` 通常是行星的 `root` Group(配置 `userData.bodyType` 在 root 上,锚点系统也以 root 为单位定位)。`root` 不是 Mesh 而是 Group,`getLocalBoundingSphere(root)` 命中非 Mesh 分支 → 走 `Box3.getBoundingSphere` → 触发上面的 1.73x 偏差。

太阳和行星都受这个影响。

## 3. 解决办法

按可控性 / 改动量 排序,从轻到重。

### 3.1 方案 A:配置 `hoverLocalRadius`(推荐)

在每个天体的配置项里加一个本地坐标系下的 hover 半径:

```js
// SunConfig / PlanetConfig
{
    // ...
    hover: {
        localRadius: 1.0,   // 本地坐标系下的半径,× maxScale 得到世界半径
    },
}
```

`getLocalBoundingSphere` 改造:**优先取配置值,没配再 fallback 到现在的算法**:

```js
function getLocalBoundingSphere(object) {
    const cacheKey = '__hoverLocalSphere'
    const cached = object.userData[cacheKey]
    if (cached !== undefined && cached !== null) return cached

    /** @type {LocalBoundingSphere} */
    const localSphere = {
        centerLocal: new THREE.Vector3(),
        radiusLocal: 0,
    }

    // 优先取调用方在 userData 上挂的配置半径
    const configured = object.userData.hoverLocalRadius
    if (typeof configured === 'number' && configured > 0) {
        // centerLocal 默认 (0, 0, 0),即"本地原点就是 hover 中心"
        localSphere.radiusLocal = configured
        object.userData[cacheKey] = localSphere
        return localSphere
    }

    // ... 原 Mesh / 非 Mesh 算法保持不变作为 fallback
}
```

天体初始化时把配置写到 root 的 userData 上(planet.js / sun.js):

```js
root.userData.hoverLocalRadius = config.hover.localRadius
```

`calcProjection` 末尾恢复成 `radiusPx = Math.hypot(deltaX, deltaY)`(去掉 /2)。

**优点**:
- 完全可控,设计期就能确定 hover 区域大小,跟模型几何解耦
- 不依赖 `Box3.getBoundingSphere` 这种"形状敏感"的算法
- 可以在不重新加载模型的情况下,微调单个天体的 hover 灵敏度
- 太阳和外行星可以分别配不同的"灵敏度倍率"(比如外行星模型小,可以配大一点的 hoverLocalRadius 让 hover 更容易触发)

**缺点**:
- 每个天体都要手动配一个数字,需要一次目测调参
- 如果模型尺寸将来变了,配置要跟着改

### 3.2 方案 B:调用方传"主体 Mesh"而非 root Group

让 `calcProjection` 始终走 Mesh 分支(`geometry.boundingSphere`),不走 `Box3.getBoundingSphere`。

需要在 hover 状态机的 `activeEntity` 上额外挂一个引用,指向"用于投影的主体 mesh":

```js
// planet.js initPlanet() 里
planet.root.userData.projectionMesh = planet.pickableMeshes[0]   // 或者主体 mesh
```

`tickHover` 计算投影时:

```js
const projTarget = activeEntity.userData.projectionMesh ?? activeEntity
const projection = calcProjection(projTarget, camera, domElement)
```

**优点**:
- 不需要手动配数字
- `geometry.boundingSphere` 比 `Box3.getBoundingSphere` 紧得多

**缺点**:
- 多模型行星(行星本体 + 装饰几何体在同一 GLTF 里)选哪个 mesh 作为主体不一定显然
- `geometry.boundingSphere` 仍然不一定等于"可见轮廓"——如果模型有外凸的小装饰,boundingSphere 会被那个小装饰拉大
- 把"投影目标 mesh"和"hover 状态机管理的实体"耦合起来,违反 hover 状态机原本的"以 root 为单位"的设计

### 3.3 方案 C:自己实现紧的 bounding sphere

针对非 Mesh 分支,改成:

```js
// 遍历 object 下所有 mesh,合并它们各自的 geometry.boundingSphere
const merged = new THREE.Sphere()
let first = true
object.traverse(child => {
    if (child.isMesh && child.geometry) {
        if (!child.geometry.boundingSphere) child.geometry.computeBoundingSphere()
        const local = child.geometry.boundingSphere.clone()
        // 把子 mesh 的 boundingSphere 变换到 object 的本地空间
        local.applyMatrix4(/* child relative to object */)
        if (first) {
            merged.copy(local)
            first = false
        } else {
            merged.union(local)
        }
    }
})
// merged 即为 object 本地空间下覆盖所有子 mesh 的紧 bounding sphere
```

**优点**:
- 不需要手动配数字
- 比 `Box3.getBoundingSphere` 紧

**缺点**:
- 实现复杂(尤其是多层嵌套时变换矩阵的处理)
- 仍然受"模型自身几何形状"影响——如果有外凸装饰,误差还在
- `Sphere.union` 算的是覆盖两个球的最小球,合并多次也不一定紧

## 4. 选型建议

**主流程跑通后,优先实施方案 A(`hoverLocalRadius` 配置项)**,理由:

1. 改动量最小,集中在 `getLocalBoundingSphere` 的入口判断 + 几个配置文件
2. 完全可控:设计期决定 hover 区域,跟"模型几何统计"完全解耦,以后换模型也不会突然失准
3. 跟项目现有的"配置驱动"风格一致(`PlanetConfig` 已经有 `scale`、`orbit`、`label` 等字段了,加一个 `hover` 字段顺势)
4. 方案 B 和 C 都治标不治本——只要还在做"从几何体推 hover 半径"这件事,就永远会受模型形状影响

方案 B 可以作为兜底:对于没配 `hoverLocalRadius` 的天体,fallback 走 mesh 路径(而不是 Box3 路径)。
