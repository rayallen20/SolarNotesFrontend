# `initEngine` 的异步错误处理

> 缘起:`engine.js` 的 `initEngine()` 函数里所有 `await` 都没有 `try/catch` 包裹,这会不会出 bug?
>
> 结论:**不会因为没 `try/catch` 而出语法 bug**——`async/await` 的错误传播机制本身是正确的。但当前写法存在**3 个健壮性问题**值得修。

## 1. `async/await` 错误传播机制(基础回顾)

```js
async function foo() {
    await willThrow()       // ① 这里抛错
    console.log('xxx')      // ② 不会执行
}

foo()                       // 返回一个 rejected Promise
foo().catch(err => ...)     // 调用方可以捕获
```

`async function` 内部任意一个 `await` 抛错,等价于 `function` 里直接 `throw`:

- 抛错点之后的语句**全部不执行**
- 函数立即"失败返回",调用方拿到的是一个 **rejected Promise**
- 真正决定后果的是**调用方**有没有处理这个 rejection

所以从机制上看,不写 `try/catch` 是合法且常见的——**异常会自然往上传**。

## 2. 当前 `initEngine` 失败时会发生什么

`engine.js` 的 `initEngine` 大致结构:

```js
export async function initEngine (container) {
    container.appendChild(renderer.domElement)        // ① canvas 已挂到 DOM
    await initSceneEnvironment(renderer)               // ←假设这里抛错 ──┐
    await initSkySphereTexture()                                          │
    scene.add(skySphere)                                                  │
    await initSun()                                                       │
    scene.add(sunAxis)                                          后续都不执行
    await initPlanets()                                                   │
    for (const planet of planets) { scene.add(planet.axis) }              │
    ...                                                                   │
    window.addEventListener('resize', onWindowResize)  // 没注册 ✓        │
    startAnimation()                                   // 没启动 ✓        │
    return dispose                                     // 没返回 ⚠️ ─────┘
}
```

如果失败发生在更靠后的位置(比如 `await initSun()`),则 `skySphere` 已经被 add 到 scene。

不同失败点留下的"残骸"对照:

|         失败位置          | DOM 上 canvas |  scene 里残留对象   |
|:-------------------------:|:-------------:|:-------------------:|
| `initSceneEnvironment` 抛 |    ✅ 已挂    |         空          |
| `initSkySphereTexture` 抛 |      ✅       |         空          |
|       `initSun` 抛        |      ✅       |      skySphere      |
|     `initPlanets` 抛      |      ✅       | skySphere + sunAxis |

只要不是**第一步就失败**,就有资源泄漏。

## 3. 3 个真正的隐患

### 3.1 部分初始化的"半成品状态"

scene 里残留的对象继续占用显存。如果调用方监听到失败后立刻重试 init,会看到 skySphere 出现两次(被 add 两次,Three.js 不去重)。

### 3.2 `dispose` 没返回,调用方无法清理(最关键)

`initEngine` 的合同是「成功 → 返回 dispose 函数」。失败时函数直接抛错,调用方拿到的是 rejected Promise,**而不是 dispose 函数**。

后果:Vue 组件 unmount 时根本找不到 dispose,canvas 留在 DOM 里、贴图占着显存,直到用户刷新页面。

### 3.3 用户体验不可控

异常默认会变成浏览器控制台的红字 + "Unhandled Promise Rejection" 警告。如果调用方(Vue 组件)没监听,用户看到的只是**一个白屏**,不知道是网络问题、贴图加载失败还是模型路径错。

## 4. 3 种解决方案

### 4.1 方案 A:调用方负责(最简单,推荐起步)

`initEngine` 不动,**调用方**(Vue 组件 `onMounted`)用 try/catch:

```vue
<script setup>
import {onMounted, onBeforeUnmount, ref} from 'vue'
import {initEngine} from '@/three/engine.js'

const containerRef = ref()
let dispose = null

onMounted(async () => {
    try {
        dispose = await initEngine(containerRef.value)
    } catch (err) {
        console.error('3D 场景初始化失败', err)
        // 显示错误 UI 给用户
    }
})

onBeforeUnmount(() => {
    dispose?.()
})
</script>
```

**适用场景**:个人 / 学习项目。
**遗留问题**:partial scene 还在(没清理)。

### 4.2 方案 B:`initEngine` 内部做"失败时回滚"(推荐生产)

把 try/catch 包在 `initEngine` 里,失败时**自己调用 dispose 清掉半成品**,再把原异常继续抛出:

```js
export async function initEngine (container) {
    container.appendChild(renderer.domElement)

    try {
        await initSceneEnvironment(renderer)
        await initSkySphereTexture()
        scene.add(skySphere)
        await initSun()
        scene.add(sunAxis)
        await initPlanets()
        for (const planet of planets) {
            scene.add(planet.axis)
        }

        if (import.meta.env.DEV) {
            const {axesHelper} = await import('@/three/base/axisHelper.js')
            scene.add(axesHelper)
        }

        controls = createOrbitControls(camera, renderer.domElement)
        initComposers()
        markAsBloomObject(sunAxis)
        window.addEventListener('resize', onWindowResize)
        startAnimation()
    } catch (err) {
        dispose()                              // 清掉已创建的资源
        renderer.domElement.remove()           // 把 canvas 从 DOM 摘掉
        scene.clear()                          // 清空 scene
        throw err                              // 原异常继续往上抛
    }

    return dispose
}
```

`dispose` 内部已经对 `controls === null`、`rafId === null` 做了 guard,所以**半成品状态下调它是安全的**:

```js
function dispose () {
    window.removeEventListener('resize', onWindowResize)   // 幂等
    if (rafId !== null) { cancelAnimationFrame(rafId); rafId = null }
    if (controls !== null) { controls.dispose(); controls = null }
    disposeBloom()
    renderer.dispose()
}
```

**适用场景**:生产环境 / 多人维护项目。
**优点**:调用方代码更简洁(只 catch + 显示错误 UI 即可);partial 状态一定被清理。

### 4.3 方案 C:每个 await 单独 try/catch + 降级

```js
try {
    await initSkySphereTexture()
    scene.add(skySphere)
} catch {
    // 天空球加载失败,降级用纯黑背景
    scene.background = new THREE.Color(0x000000)
}
```

**适用场景**:某个资源失败时**有合理的降级方案**(比如天空球失败 → 纯黑背景)。
**这个项目不适用**:所有资源都是必须的,失败就只能整体停下,做不出有意义的降级。

## 5. 推荐路径

1. **当下最实用**:**做方案 A**——5 行代码,确保调用方(Vue 组件)有 try/catch,至少错误能进 console、组件能正常 unmount
2. **进阶**:迁移到**方案 B**,把"失败回滚"内化到 `initEngine`,降低调用方的心智负担
3. 顺便给 `initEngine` 的 JSDoc 加一行,明确异常契约:

```js
* @throws {Error} 任意一个异步资源加载失败时抛出;此时调用方无需调用 dispose,内部已自行清理
```

## 6. 要点提炼

- `async/await` 不写 `try/catch` 不是 bug——异常会自然往调用链上传
- 真正的问题是:**资源在异常点之前已经分配,但分配的清理路径(dispose)没返回给调用方**
- 异步初始化函数的健壮做法是:**要么调用方接管 try/catch + 自行清理;要么 init 函数内部 try/catch + 失败回滚再抛**
- 对外暴露的"成功返回 dispose"合同,在失败路径上要么"承诺已自行清理"、要么"由调用方处理"——两者必择其一,不能两边都不管
