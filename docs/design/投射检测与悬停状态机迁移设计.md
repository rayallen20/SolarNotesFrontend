# 投射检测 + 悬停状态机 迁移设计

> 对应 `迁移规划.md` 的**阶段 8**(原文档已规划"引入 Pinia 状态管理")。
> 本文档不是简单的"原代码搬运清单"——而是基于对原项目代码的诊断,给出一个**重新切分职责的设计方案**。
> 目标是:把 `universeBlog/src/interaction/hover.js`、`base/raycaster.js`、`ui/label/label.js`(其中状态机相关部分)、`lib/pointer.js`、`lib/projection.js`、`lib/findAncestorByName.js` 这一组在原项目里**互相耦合的模块**,在 Vue + Pinia 下重新组织为单一职责、可测、可拆的结构。

---

## 1. 范围

### 1.1 本次迁移**包含**

| 原文件 | 处理方式 |
| --- | --- |
| `src/base/raycaster.js` | 重写为纯函数 + 一次性可拾取列表注册 |
| `src/interaction/hover.js`(state + tickHover + 4 个 enter*) | 状态拆到 Pinia,逻辑保留为纯 tick 函数 |
| `src/lib/pointer.js`(NDC 转换) | 直接迁移,无需重构 |
| `src/lib/projection.js`(calcProjection + distanceToProjectionEdgePx) | 直接迁移,无需重构 |
| `src/lib/findAncestorByName.js` | 直接迁移 |
| `src/ui/label/label.js` 中的 `isNearLabel` / `isFarLabel` / `pointToRectDistancePx` | 拆出为独立的几何工具模块 |
| 原 `index.js` 中的 `pointerdown` / `pointerup` / `pointermove` / `pointerenter` / `pointerleave`(画布上)以及 `checkHover` 中关于悬停的部分 | 改写到 `SolarCanvas.vue` 的 `onMounted` / `onBeforeUnmount` 与 `engine.js` 的动画循环 |
| 原 `label.js` 中 label DOM 上的 `pointerenter` / `pointerleave` | 改写到 `SolarLabel.vue` 的模板事件 |

### 1.2 本次迁移**不包含**

- `focus.js`(点击聚焦 + 相机动画) — 属于阶段 9
- `calcOffset.js` / `worldToScreen.js`(label 屏幕位置计算) — 属于"label 显示位置"的子任务,与状态机逻辑正交。本次迁移只保证状态机能正确驱动 label 显隐,**不接管 label 在哪里显示**。位置计算等到状态机就位、能稳定输出"当前 active body 的引用"后再做单独的小任务。
- 原 `index.js` 中点击聚焦的逻辑(`pointerdown`/`pointerup` + 阈值判断 + `focusOn`) — 留给阶段 9

> 这样切分的好处:**每完成一个阶段都可以独立验收**——哪怕 label 位置暂时是 `(0, 0)` 也能验证悬停状态机的正确性。

## 2. 现状诊断:原代码"乱"在哪里

### 2.1 模块职责模糊

`label.js` 同时负责:
1. DOM 查询(`document.querySelector`)
2. 注册 label 的 `pointerenter/leave` 事件,**直接修改 `state.pointer.isLabelHover`**
3. 显示/隐藏 label(写 `style.opacity` / `visibility` / `pointerEvents`)
4. 写文案(`titleElement.textContent = ...`)
5. 算位置(`worldToScreen` + `calcOffset`)
6. 注册按钮 click,触发 `focusOn`(跨模块跳转)
7. 暴露纯几何函数 `isNearLabel` / `isFarLabel` / `pointToRectDistancePx`

**7 件事在一个文件里,而且互相依赖**——Vue 化时无法直接抄,必须先拆开。

### 2.2 共享状态是裸的可变模块单例

`hover.js` 顶部 `export const state = {...}`,所有跟悬停有关的字段(包括"鼠标 NDC 坐标"、"label 矩形"、"sticky 时间戳"、"locked 标记")都堆在一个对象里。
- 没有访问控制——任何模块都可以 `state.foo = bar`(`label.js` 就这么做了)。
- 没有响应式——Vue 模板想消费这些字段,得靠每帧轮询。
- 不可测——状态机逻辑和具体存储方式绑死。

### 2.3 派生量被存为状态

```js
// hover.js: tickHover() 里
state.active.locked = state.pointer.isLabelHover || state.pointer.isNearLabel
```

`locked` 完全可以从 `isLabelHover || isNearLabel` 即时算出,但原代码把它存为状态字段,带来"什么时候刷新"的耦合(必须在 tickHover 里手动赋值,顺序错了就脏数据)。

### 2.4 状态机与"宿主"逻辑混在一起

`tickHover` 内做了 4 件事:
1. 刷新当前激活天体的投影(`flushProjection`)
2. 派生 `active.locked`
3. 防御性提前 return(`hasEverMoved` 检查)
4. 4 段 `if (phase === 'xxx')` 的转移逻辑(且用的是连续 `if`,不是 `switch`/`else if`,容易因转移后忘记 `return` 而连锁触发)

这种结构混在一起,改任何一段都要担心副作用。

### 2.5 渲染循环的悬停部分跨两个函数

原 `index.js` 的 `animate()` 里:
```js
tickHover(now, camera, renderer.domElement)
let freeze = isFocused()
if (!isFocused()) freeze = checkHover()
```

而 `checkHover` 函数体里又调用 `showLabel`(写 DOM) + 拿 label rect 写回 `state` + `isNearLabel` 滞回判断。**数据流是 `输入 → state → DOM → DOMRect → state`**,链路太长,出 bug 时不知道从哪段查起。

### 2.6 raycaster 模块依赖反向

```js
// base/raycaster.js
import {pickableMeshes as sunPickableMeshes} from "../sun"
import {getAllPickableMeshes} from "../planet/planets"
```

`base` 反向依赖 `sun` 与 `planet`——base 应当是更"低层"的引擎能力,却挂在了具体业务模型上。`setPickAble()` 的调用时机也是隐式契约(必须在所有天体初始化后调用,否则数组是空的)。

## 3. 重构原则

| 原则 | 含义 |
| --- | --- |
| **单一职责** | 每个模块只做一件事:几何计算 / 状态管理 / 状态机推进 / 事件绑定 / DOM 渲染。 |
| **共享状态走 Pinia,且只走 Pinia** | 不再有裸 `export const state`。组件和 three 层都通过 store 通信,store 是唯一可信源。 |
| **派生量用 computed,不存** | `shouldShowLabel` / `shouldFreezeRevolution` / `isActiveLocked` 等都是 getter。 |
| **副作用在边界处,纯逻辑在中间** | tickHover 改写为纯函数,状态机不直接访问 DOM,DOM 操作集中在 Vue 组件的事件回调。 |
| **依赖方向只能向下** | `base` 不依赖 `planet`/`sun`;raycaster 接受可拾取列表作为参数(或由 `engine.js` 显式注册一次)。 |
| **几何工具是纯函数** | `calcProjection` / `pointToRectDistancePx` / `getNDCCoordinate` 等无副作用,可独立单测。 |
| **生命周期对齐 Vue** | 所有 `addEventListener` 必须在 `onBeforeUnmount` / `dispose()` 配对清理。 |

### 5.4 `src/three/lib/rect.js`(新)

把原 `label.js` 里和 label DOM 形状无关的纯几何函数抽出来:

```js
/**
 * 计算屏幕上一个点到一个矩形最近边的距离(若点在矩形内,返回 0)
 * @param {DOMRect} rect
 * @param {{x: number, y: number}} point
 * @return {number} 像素距离
 */
function pointToRectDistancePx(rect, point) {
    let dx = 0
    if (point.x < rect.left) dx = rect.left - point.x
    else if (point.x > rect.right) dx = point.x - rect.right

    let dy = 0
    if (point.y < rect.top) dy = rect.top - point.y
    else if (point.y > rect.bottom) dy = point.y - rect.bottom

    return Math.hypot(dx, dy)
}

function isNearRect(rect, point, enterDistancePx) {
    return pointToRectDistancePx(rect, point) <= enterDistancePx
}

function isFarRect(rect, point, exitDistancePx) {
    return pointToRectDistancePx(rect, point) >= exitDistancePx
}

export { pointToRectDistancePx, isNearRect, isFarRect }
```

> 命名从 `isNearLabel`/`isFarLabel` 改为 `isNearRect`/`isFarRect` —— 它们是纯几何函数,与 label 这个具体业务无关。

### 5.5 `src/three/lib/findAncestorByName.js`

### 5.6 `src/three/base/raycaster.js`(重写)

去掉对 `sun` / `planet` 的反向依赖。

```js
import * as THREE from 'three'

/**
 * @type {THREE.Raycaster}
 */
const raycaster = new THREE.Raycaster(
    new THREE.Vector3(0, 0, 0),
    new THREE.Vector3(0, 0, -1),
    0,
    Infinity
)

/**
 * @type {Array<THREE.Mesh>} 当前注册的可拾取网格列表
 */
let pickables = []

/**
 * 由调用方(engine.js)在所有天体加载完成后注册一次
 */
function setPickables(meshes) {
    pickables = meshes
}

/**
 * 纯函数:返回当前射线第一个命中的对象,无命中返回 null
 */
function pickHoveredBody(mouseNDC, camera) {
    raycaster.setFromCamera(mouseNDC, camera)
    const intersects = raycaster.intersectObjects(pickables, false)
    return intersects.length === 0 ? null : intersects[0].object
}

export { setPickables, pickHoveredBody }
```

依赖方向变成:**`engine.js`(知道太阳和行星) → 调用 `setPickables(...)` → 注入到 `raycaster`**。`raycaster` 不再知道天体的存在。

> 命名变化:`findHoveringObject` → `pickHoveredBody`(更短、更准——"pick"是 three 圈的标准词)。原命名也可保留,看你偏好。

### 5.7 `src/stores/hover.js`(新,Pinia store)

> **核心数据流枢纽**。SolarCanvas 写入,SolarLabel 读取与上报 rect / 自身 hover 状态,three/interaction/hover.js 的 `tickHover` 读取 + 调用 actions 推进。

字段切分为 5 组:

```js
import {defineStore} from 'pinia'
import {ref, computed, shallowRef} from 'vue'
import * as THREE from 'three'
import {HoverPhase} from '@/lib/enum.js'

/**
 * @typedef {Object} Pointer 鼠标输入快照,由 SolarCanvas 的 DOM 事件每帧写入
 * @property {import('three').Vector2} ndcCoordinate 鼠标在canvas中的NDC坐标,Z分量略,默认值(0,0)
 * @property {{x: Number, y: Number}} screenPx 鼠标在视口下的屏幕像素坐标(相对视口左上角)
 * @property {Boolean} inCanvas 鼠标当前是否在canvas DOM元素内
 * @property {Boolean} hasEverMoved 自页面加载以来,鼠标是否触发过至少一次pointermove事件
 * */

/**
 * @typedef {Object} StickyState 粘滞区(sticky)阶段的配置项和运行时状态
 * @property {Number} enterEdgeDistancePx 配置项: 由body进入sticky的距离阈值(单位: 像素)
 * @property {Number} exitEdgeDistancePx 配置项: 由sticky退出到idle的距离阈值(单位: 像素)
 * @property {Number} expireMs 配置项: 粘滞效果的最长保留时长,超过该时长后即使鼠标仍停留在粘滞区,粘滞效果也要结束 (单位: 毫秒)
 * @property {Number} minHoldMs 配置项: 粘滞效果的最短保留时长,在该时长内即使鼠标离开粘滞区,粘滞效果也不会结束 (单位: 毫秒)
 * @property {Number} startedAt 运行时: 进入sticky阶段的时间戳(单位: 毫秒,基准为performance.now()),0表示未进入
 * */

/**
 * @typedef {Object} LabelHysteresis label接近度滞回判定的距离阈值
 * @property {Number} enterDistancePx 由"远离label"切到"接近label"的距离阈值(单位: 像素)
 * @property {Number} exitDistancePx 由"接近label"切到"远离label"的距离阈值(单位: 像素)
 * */

/**
 * @typedef {Object} LabelText 显示在label上的文本内容,由activeEntity派生
 * @property {String} title label的标题(对应天体userData中的title字段)
 * @property {String} intro label的介绍(对应天体userData中的intro字段)
 * */

export const useHoverStore = defineStore('hover', () => {
    /* ---------- 1. 阶段(状态机当前所在节点) ---------- */
    /** @type {import('vue').Ref<String>} 当前状态机所在的阶段,取值范围见HoverPhase枚举 */
    const phase = ref(HoverPhase.idle)

    /* ---------- 2. 当前激活的天体 + 投影 ---------- */
    // shallowRef:Object3D 不需要 Vue 深度代理(性能 + 防止 three.js 内部状态被 Proxy 污染)
    /**
     * @type {import('vue').ShallowRef<import('three').Object3D|null>} 状态机当前认定的"焦点天体"
     *      - idle阶段: null
     *      - body阶段: 本帧raycaster命中的天体(且hit !== null时刚被enterBody()写入)
     *      - sticky阶段: 从body阶段进入sticky时携带过来的天体,不随本帧raycaster是否命中而变
     *        (sticky的定义即"已离开body投影边界,但尚未离开粘滞区")
     *      - label阶段: 从body/sticky阶段进入label时锁定的天体,
     *        因isActiveLocked为true,本帧raycaster命中谁都不切换
     *      Tips: 每帧raycaster的瞬时结果由tickHover作为局部变量持有,
     *      不升格为store字段——activeEntity只反映"焦点",不反映"瞬时命中"
     * */
    const activeEntity = shallowRef(null)

    /** @type {import('vue').Ref<import('@/three/lib/projection.js').ScreenProjection>} 当前激活天体的屏幕投影信息,每帧由tickHover更新 */
    const activeProjection = ref({
        centerPx: {x: 0, y: 0},
        radiusPx: 0,
        ndcZ: 0,
    })

    /* ---------- 3. 鼠标 ---------- */
    // 不需要响应式,只在 tickHover 里被 raycaster / 几何函数读
    // 用普通对象避免 Proxy 开销
    /** @type {Pointer} */
    const pointer = {
        ndcCoordinate: new THREE.Vector2(0, 0),
        screenPx: {x: 0, y: 0},
        inCanvas: false,
        hasEverMoved: false,
    }

    /* ---------- 4. label 相关(由 SolarLabel 写,tickHover 读) ---------- */
    /** @type {import('vue').ShallowRef<DOMRect|null>} label的屏幕矩形,由SolarLabel在ResizeObserver中写入,未渲染时为null */
    const labelRect = shallowRef(null)

    /** @type {import('vue').Ref<Boolean>} 鼠标是否落在label DOM元素内(由SolarLabel的pointerenter/leave维护) */
    const isLabelHover = ref(false)

    /** @type {import('vue').Ref<Boolean>} 鼠标是否"接近"label(滞回判定的结果,由tickHover维护) */
    const isNearLabel = ref(false)

    /* ---------- 5. sticky(粘滞区)状态 ---------- */
    /** @type {StickyState} */
    const sticky = {
        enterEdgeDistancePx: 24,
        exitEdgeDistancePx: 36,
        expireMs: 1500,
        minHoldMs: 300,
        startedAt: 0,
    }

    /** @type {LabelHysteresis} */
    const labelHysteresis = {
        enterDistancePx: 8,
        exitDistancePx: 14,
    }

    /* ---------- 派生量(computed) ---------- */
    /** @type {import('vue').ComputedRef<Boolean>} 是否应显示label(任何非idle阶段都显示) */
    const shouldShowLabel = computed(() => phase.value !== HoverPhase.idle)

    /** @type {import('vue').ComputedRef<Boolean>} 是否应冻结公转(任何非idle阶段都冻结) */
    const shouldFreezeRevolution = computed(() => phase.value !== HoverPhase.idle)

    /** @type {import('vue').ComputedRef<Boolean>} 当前激活实体是否被锁定(指针在label上或接近label时锁定,防止label因鼠标移开而消失) */
    const isActiveLocked = computed(() => isLabelHover.value || isNearLabel.value)

    /** @type {import('vue').ComputedRef<LabelText|null>} label应显示的文本,activeEntity为null时返回null */
    const labelText = computed(() => {
        const entity = activeEntity.value
        if (entity === null) return null
        return {title: entity.userData.title, intro: entity.userData.intro}
    })

    /* ---------- Actions:状态机转移 ---------- */

    /**
     * 切回idle阶段并清理所有运行时状态(active天体、labelRect、isNearLabel、sticky计时)
     * Tips: 不重置isLabelHover —— 该字段由SolarLabel的pointerleave事件独立维护
     * */
    function enterIdle() {
        phase.value = HoverPhase.idle
        activeEntity.value = null
        labelRect.value = null
        isNearLabel.value = false
        sticky.startedAt = 0
    }

    /**
     * 由idle切到body阶段,记录命中的天体
     * @param {import('three').Object3D} hitObject 命中的天体对象(通常是行星的root group或太阳的root group)
     * */
    function enterBody(hitObject) {
        // 防御:理论上正常状态机流程下,处于 label 阶段(isActiveLocked === true)时
        // 不会有人调 enterBody —— tickHover 在 label 阶段不会试图切回 body。
        // 此处兜底是为了防御"外部代码绕过 actions 直接修改 store 中的字段"以及
        // "未来重构破坏不变量"两种场景,详见 5.8.2。
        if (isActiveLocked.value) return
        phase.value = HoverPhase.body
        activeEntity.value = hitObject
    }

    /**
     * 由body切到sticky阶段,记录进入时间
     * @param {Number} nowMs 当前时间戳(单位: 毫秒,基准为performance.now())
     * */
    function enterSticky(nowMs) {
        phase.value = HoverPhase.sticky
        sticky.startedAt = nowMs
    }

    /**
     * 由sticky切到label阶段,清空sticky计时
     * */
    function enterLabel() {
        phase.value = HoverPhase.label
        sticky.startedAt = 0
    }

    /* ---------- Actions:外部世界 → store ---------- */

    /**
     * 将鼠标的NDC坐标写入store
     * @param {Number} x NDC坐标的x分量,有效范围[-1, 1],超出表示鼠标在canvas外
     * @param {Number} y NDC坐标的y分量,有效范围[-1, 1],超出表示鼠标在canvas外
     * */
    function setPointerNDC(x, y) {
        pointer.ndcCoordinate.set(x, y)
    }

    /**
     * 将鼠标的屏幕像素坐标写入store
     * @param {Number} x 屏幕像素坐标的x分量(相对视口左上角)
     * @param {Number} y 屏幕像素坐标的y分量(相对视口左上角)
     * */
    function setPointerScreen(x, y) {
        pointer.screenPx.x = x
        pointer.screenPx.y = y
    }

    /**
     * 设置鼠标当前是否在canvas DOM元素内
     * @param {Boolean} flag true表示鼠标在canvas内,false表示在外
     * */
    function setPointerInCanvas(flag) {
        pointer.inCanvas = flag
    }

    /**
     * 标记鼠标已经触发过至少一次pointermove事件(单调标志,一旦置true不会再回false)
     * */
    function markPointerMoved() {
        pointer.hasEverMoved = true
    }

    /**
     * 写入label的屏幕矩形(由SolarLabel在ResizeObserver/MutationObserver中调用)
     * @param {DOMRect|null} rect label的当前屏幕矩形,label未渲染时传null
     * */
    function setLabelRect(rect) {
        labelRect.value = rect
    }

    /**
     * 设置鼠标是否落在label DOM元素内
     * @param {Boolean} flag true表示在内,false表示在外
     * */
    function setLabelHover(flag) {
        isLabelHover.value = flag
    }

    /**
     * 设置鼠标是否"接近"label(滞回判定结果)
     * @param {Boolean} flag true表示接近,false表示远离
     * */
    function setNearLabel(flag) {
        isNearLabel.value = flag
    }

    /**
     * 写入当前激活天体的屏幕投影信息
     * Tips: 直接 ref.value = obj 会触发整对象 reactivity;projection 每帧都改,
     * 但 SolarLabel 的位置 binding 又依赖它 —— 用 ref 是对的(reactivity 是必要的)
     * @param {import('@/three/lib/projection.js').ScreenProjection} projection 屏幕投影信息
     * */
    function setActiveProjection(projection) {
        activeProjection.value = projection
    }

    return {
        // state
        phase, activeEntity, activeProjection,
        pointer,                                     // 普通对象,直接挂上
        labelRect, isLabelHover, isNearLabel,
        sticky, labelHysteresis,

        // computed
        shouldShowLabel, shouldFreezeRevolution, isActiveLocked, labelText,

        // actions: phase transitions
        enterIdle, enterBody, enterSticky, enterLabel,

        // actions: input setters
        setPointerNDC, setPointerScreen, setPointerInCanvas, markPointerMoved,
        setLabelRect, setLabelHover, setNearLabel, setActiveProjection,
    }
})
```

#### 5.7.1 关于响应式粒度

- `phase` / `activeEntity` / `activeProjection` / `labelRect` / `isLabelHover` / `isNearLabel` 必须是 ref —— 模板要消费。
- `pointer` 是普通对象 —— 它每帧高频更新,且没有任何模板需要直接显示鼠标坐标,响应式只会浪费性能。`tickHover` 直接读 `pointer.ndcCoordinate` 即可。
- `sticky` / `labelHysteresis` 是普通对象 —— 配置量 + 运行时计时器,模板用不到。
- `activeEntity` 用 `shallowRef` —— `THREE.Object3D` 是复杂对象,深度 reactive 既无意义又会触发 three.js 内部状态变更时的级联 reactivity 风暴。

#### 5.7.2 关于 `enterSticky(nowMs)` —— 为什么时间作为参数传入

`enterSticky` 的签名是 `enterSticky(nowMs)` 而不是 `enterSticky()` 内部自己调 `performance.now()`,这是一个有意为之的设计选择。同样的设计原则也应用于 `tickHover(nowMs, camera, domElement)` 自身——tickHover 也不调 `performance.now()`,由 engine.js 的 animation loop 喂入。

理由按重要性排序如下。

##### 1. 同一 tick 内的时间一致性(最重要)

`tickHover` 一次调用代表"渲染一帧",一帧内可能多处用到"现在是几点":

```js
function tickHover(nowMs, camera, domElement) {
    // body 分支:决定要不要进 sticky
    if (...) {
        store.enterSticky(nowMs)
    }

    // sticky 分支:检查超时
    const elapsed = nowMs - store.sticky.startedAt
    if (elapsed >= store.sticky.expireMs) { ... }
}
```

`nowMs` 在整个 tick 内是一个常量——它是这一帧的"权威时刻"。所有决策(进入 sticky、判 `expireMs`、判 `minHoldMs` 等)**都基于这同一个时刻**。

如果 `enterSticky` 内部自己拿 `performance.now()`,问题就出现了:

```
tickHover 在 t=100.000 时拿到 nowMs = 100.000
走到 enterSticky 时,JS 又跑了一会儿,内部 performance.now() 拿到 100.317
sticky.startedAt 被记成了 100.317

下一帧 t=116.667,tickHover 拿到 nowMs = 116.667
elapsed = 116.667 - 100.317 = 16.350  ← 算出来的间隔少了 0.317ms
```

虽然亚毫秒级偏差在 UI 交互上几乎看不出来,但本质上是两个时间体系在做减法:`nowMs` 系列 vs `enterSticky 内部各自的 now` 系列。这种"看似无害的不一致"正是日后排查"为什么 `minHoldMs` / `expireMs` 行为偶尔不对"时最难定位的 bug 来源。

把 `nowMs` 作为参数传入,**强制所有时间计算都在同一个坐标系下**——免费且无副作用。

##### 2. tickHover 才是时间源的真正持有者,enterSticky 不是

`enterSticky` 是 store 里的 action,语义是"切换到 sticky 阶段并记录起点时刻"。**"起点时刻"是输入,不是它该决定的东西**。决定"什么是现在"是更上层的责任:

```
浏览器 requestAnimationFrame  → frameTimeMs(精确到该帧的浏览器时钟)
    ↓
engine.js 的 animate(frameTimeMs)
    ↓
tickHover(frameTimeMs, camera, domElement)
    ↓
内部所有决策、所有传给 actions 的 nowMs,都用这一个 frameTimeMs
```

`requestAnimationFrame` 的回调本身就带一个 `time` 参数,这是浏览器给的、精确到该帧的时间。理想形式:

```js
function animate(frameTimeMs) {
    requestAnimationFrame(animate)
    tickHover(frameTimeMs, camera, domElement)
}
requestAnimationFrame(animate)
```

这就连 `performance.now()` 都不用调——直接用浏览器给的最权威的帧时间。**如果 `enterSticky` 自己内部调 `performance.now()`,这条干净的传递链就被打断了**——失去了"frameTimeMs 是这一帧唯一时间源"的不变量。

##### 3. 可测试性

```js
// 时间作为参数:确定性测试
test('进入 sticky 时正确记录起点', () => {
    store.enterSticky(1000)
    expect(store.sticky.startedAt).toBe(1000)
})

// 时间作为内部副作用:必须 mock 全局
test('进入 sticky 时正确记录起点', () => {
    store.enterSticky()
    expect(store.sticky.startedAt).toBe(/* ??? */)
    //                                 必须 mock performance.now 或者断言"差不多"
})
```

action 把时间作为参数后,它就是一个**纯函数风格的状态变更**——给定相同输入,产生相同状态。这种性质让单元测试不需要任何时间 mock。本工程目前没在写单测,但代码结构本身的可测性是一种长期价值——它意味着函数没有隐藏的外部依赖(global state、当前时间、网络等),逻辑上自我封闭。

##### 4. 时间源可替换

只要 store 的 action 不偷偷调 `performance.now()`,下列场景都不需要改 store,只改 engine.js 一处:

- **录制 / 回放**:把每帧的 `frameTimeMs` 记录下来,回放时按记录值喂给 `tickHover` —— 完全可重现
- **暂停模式**(调试时按 P 键暂停)—— 此时不调 `tickHover`,或者喂同一个固定值
- **慢动作 / 快进**(展示某个交互细节)—— 给 `tickHover` 喂一个被拉伸 / 压缩过的时间

反过来,如果 `enterSticky` 内部自己拿时间,每个使用 `performance.now()` 的 action 都要单独改造——这是典型的"时间依赖泄露"。

##### 一句话总结

> **时间是输入,不是副作用。** 把它作为参数传进来,意味着承认了这个函数依赖时间,并且把"什么时刻"的决定权留给了真正知道答案的上层(engine.js 的 animation loop)。`enterSticky` 只关心"我被告知是 X 时刻进入 sticky 的,我把它记下来"——这正是它该做的全部事情。

#### 5.7.3 关于 store 实例的类型别名 —— 让 IDE 认识 `store` 参数

5.8 的 `tickHover(nowMs, store, camera, domElement)` 把 `store` 作为参数传入(与 5.7.2 同一脉络:**显式依赖优于隐式获取**)。但这种写法有一个连带问题——IDE 不知道形参 `store` 到底是什么类型,导致 `store.xxx` 没有任何属性 / action 补全。

解决办法:在 `src/stores/hover.js` 文件末尾(`defineStore(...)` 调用结束之后)加一个 typedef:

```js
export const useHoverStore = defineStore('hover', () => {
    // ... store 内部实现 ...
    return { /* ... */ }
})

/**
 * @typedef {ReturnType<typeof useHoverStore>} HoverStore 状态机的store实例
 * */
```

然后所有以 `store` 作为参数的外部函数,都用这个类型:

```js
// src/three/interaction/hover.js

/**
 * @param {Number} nowMs
 * @param {import('@/stores/hover.js').HoverStore} store
 * @param {import('three').PerspectiveCamera} camera
 * @param {HTMLCanvasElement} domElement
 * */
function tickHover(nowMs, store, camera, domElement) {
    store.        // ← 完整的字段 / action 补全
}

/**
 * @param {Number} nowMs
 * @param {import('@/stores/hover.js').HoverStore} store
 * @param {import('three').PerspectiveCamera} camera
 * @param {HTMLCanvasElement} domElement
 * */
function handleBody(nowMs, store, camera, domElement) { ... }
```

##### 为什么这样写

`ReturnType<typeof useHoverStore>` 三段拆解:

| 部分 | 作用 |
|---|---|
| `import('@/stores/hover.js')` | 引用整个 store 模块 |
| `.useHoverStore` 配合 `typeof` | 把 `useHoverStore` 这个 const 从"值"转为"类型" |
| `ReturnType<...>` | 取该函数的返回值类型——即 Pinia 包装后的 store 实例的完整类型 |

JSDoc 完整支持 TypeScript 的工具类型(`ReturnType` / `Parameters` / `Pick` 等),IDE(基于 TS Server)会自动解析出 store 上所有的 ref / computed / action,并给出补全。

##### typedef 放在文件末尾的理由

- **语义自然**:这个类型是从 `useHoverStore` 的返回值派生而来,放在 `useHoverStore` 声明之后,逻辑顺序更清晰
- **不打断阅读流程**:文件前半部分依次是组件类型 typedef、store 主体,末尾是"对外暴露的派生类型",层次清楚
- **TS 类型层面的声明提升**:即便 typedef 放在 const 之前,`typeof useHoverStore` 也能解析——但放在末尾**更符合"先定义、再派生"的阅读习惯**

##### 为什么不直接在 `tickHover` 里 `useHoverStore()`(不传参数)

Pinia store 是全局单例,理论上可以:

```js
import {useHoverStore} from '@/stores/hover.js'

function tickHover(nowMs, camera, domElement) {
    const store = useHoverStore()   // IDE 天然知道类型
    // ...
}
```

这种写法省去了 `store` 参数,IDE 也不需要任何额外 JSDoc。但与 5.7.2 的设计哲学冲突——函数签名不再"诚实",光看 `tickHover(nowMs, camera, domElement)` 看不出它依赖 store,且单测时必须先 setup Pinia 才能调用。

所以本工程统一采用"**显式 + 类型别名**"的方案:

- 显式把 `store` 写进签名,与 `nowMs` 同等待遇
- 用 `HoverStore` 这个短类型别名让签名不至于过长
- 让 store 这个依赖跟时间一样,在函数签名上"看得见、可替换、可测试"

##### 推广到其他 store

将来若新增其他 store(如 `useCameraStore` / `useSceneStore`),应**遵循同样的约定**:

1. 每个 store 文件末尾导出一个 `<StoreName>Store` 类型别名
2. 所有以这个 store 作为参数的外部函数,用 `import('@/stores/xxx.js').<StoreName>Store` 标注 `@param`

### 5.8 `src/three/interaction/hover.js`(新)

> 状态机的"算法"。**不导出 state**,只导出 `tickHover`。

```js
import { pickHoveredBody } from '@/three/base/raycaster.js'
import { calcProjection, distanceToProjectionEdgePx } from '@/three/lib/projection.js'
import { isNearRect, isFarRect } from '@/three/lib/rect.js'
import { hoverPhase } from '@/lib/enum.js'

/**
 * 逐帧推进悬停状态机
 * @param {number} nowMs                    当前时间戳(毫秒)
 * @param {ReturnType<import('pinia').StoreDefinition>} store   useHoverStore() 返回值
 * @param {import('three').PerspectiveCamera} camera
 * @param {HTMLElement} domElement          渲染场景的 DOM 元素(canvas)
 */
function tickHover(nowMs, store, camera, domElement) {
    // 1. 防御性:鼠标从未移动过(刚加载 + 鼠标默认在 (0,0)),强制 idle
    if (!store.pointer.hasEverMoved) {
        if (store.phase !== hoverPhase.idle) store.enterIdle()
        return
    }

    // 2. 刷新当前激活天体的屏幕投影(每帧都做,因为天体在公转)
    if (store.activeEntity !== null) {
        store.setActiveProjection(calcProjection(store.activeEntity, camera, domElement))
    }

    // 3. 维护 isNearLabel 的滞回判定(严进 / 宽出)
    //    必须在阶段分发之前完成 —— 各 handler 读取的 isActiveLocked 派生自 isNearLabel,
    //    顺序错了会拿到上一帧的滞后值
    //
    //    输入 snapshot:下面三个 if 的条件需要"互不干涉",但 setNearLabel 会同步改写
    //    store.isNearLabel,若条件中直接读 store.isNearLabel,前一个 if 的写入会污染后一个 if
    //    (典型:严进成功后第二个 if 的条件也会变 true,在退化配置 enter ≥ exit 下结果会被覆盖)。
    //    把"本帧入口状态"固化进局部变量,三个 if 全部读 snapshot,语义上是 (hasLabel, wasNear)
    //    这张 2×2 真值表的并行分发,且不依赖配置不变量。
    const hasLabel = store.labelRect !== null
    const wasNear = store.isNearLabel

    // 严进:label 在 && 之前不近 → 鼠标新进入近邻区
    if (hasLabel && !wasNear) {
        store.setNearLabel(isNearRect(store.labelRect, store.pointer.screenPx, store.labelHysteresis.enterDistancePx))
    }
    // 宽出:label 在 && 之前已近 → 检查是否离开够远
    if (hasLabel && wasNear) {
        store.setNearLabel(!isFarRect(store.labelRect, store.pointer.screenPx, store.labelHysteresis.exitDistancePx))
    }
    // 复位:label 不在 && 之前却仍认为靠近 → 强制清除
    if (!hasLabel && wasNear) {
        store.setNearLabel(false)
    }

    // 4. 按当前阶段分发
    // 防御:理论上 phaseHandlers[store.phase] 不会是 undefined。
    // 不变量推导:store.phase 的所有写入都通过 4 个 action,每个 action 写入的都是 HoverPhase 枚举值;
    // phaseHandlers 字典的 4 个 key 恰好是这 4 个枚举值,所以三者一一对应,handler 永远有定义。
    // 此处兜底是为了防御"外部代码绕过 actions 直接 store.phase = '...'"以及
    // "未来扩展 HoverPhase 枚举但忘了同步 phaseHandlers"两种场景,详见 5.8.2。
    const handler = phaseHandlers[store.phase]
    if (handler !== undefined) {
        handler(nowMs, store, camera, domElement)
    }
}

const phaseHandlers = {
    [hoverPhase.idle]: handleIdle,
    [hoverPhase.body]: handleBody,
    [hoverPhase.sticky]: handleSticky,
    [hoverPhase.label]: handleLabel,
}

function handleIdle(nowMs, store, camera) {
    const hit = pickHoveredBody(store.pointer.ndcCoordinate, camera)
    if (hit !== null) store.enterBody(hit)
}

function handleBody(nowMs, store, camera, domElement) {
    // 优先级 1:label / near label —— 直接进 label 阶段
    if (store.isActiveLocked) {
        store.enterLabel()
        return
    }

    // 优先级 2:仍命中某个天体
    const hit = pickHoveredBody(store.pointer.ndcCoordinate, camera)
    if (hit !== null) {
        if (hit !== store.activeEntity) store.enterBody(hit)
        return
    }

    // 优先级 3:进入粘滞环
    const dist = distanceToProjectionEdgePx(
        store.pointer.screenPx,
        store.activeProjection.centerPx,
        store.activeProjection.radiusPx,
    )
    if (dist > 0 && dist < store.sticky.enterEdgeDistancePx) {
        store.enterSticky(nowMs)
        return
    }

    // 否则:idle
    store.enterIdle()
}

function handleSticky(nowMs, store, camera, domElement) {
    // 防御:理论上 phase === 'sticky' 时 activeEntity 不可能为 null。
    // 不变量推导:activeEntity = null 只由 enterIdle 触发,enterIdle 同时会把 phase 改成 idle 而非 sticky;
    // enterSticky / enterLabel 都不动 activeEntity,所以走到 handleSticky 时 activeEntity 一定还是
    // 上一次 enterBody 写入的那个非 null 对象。
    // 此处兜底是为了防御"外部代码绕过 actions 直接 store.activeEntity = null"以及
    // "未来重构破坏不变量"两种场景,详见 5.8.2。
    if (store.activeEntity === null) {
        store.enterIdle()
        return
    }

    // 优先级 1:进入 label
    if (store.isActiveLocked) {
        store.enterLabel()
        return
    }

    // 优先级 2:命中天体
    const hit = pickHoveredBody(store.pointer.ndcCoordinate, camera)
    if (hit !== null && !store.isActiveLocked) {
        store.enterBody(hit)
        return
    }

    // 优先级 3:超时
    const elapsed = nowMs - store.sticky.startedAt
    if (elapsed >= store.sticky.expireMs) {
        store.enterIdle()
        return
    }

    // 优先级 4:超过最短保留时长后,检查距离是否退出粘滞区
    if (elapsed < store.sticky.minHoldMs) return
    const dist = distanceToProjectionEdgePx(
        store.pointer.screenPx,
        store.activeProjection.centerPx,
        store.activeProjection.radiusPx,
    )
    if (dist >= store.sticky.exitEdgeDistancePx) store.enterIdle()
}

function handleLabel(nowMs, store, camera) {
    // 仍在 label 上 / 近 label —— 保持
    if (store.isActiveLocked) return

    // 离开 label 后,若直接命中天体
    const hit = pickHoveredBody(store.pointer.ndcCoordinate, camera)
    if (hit !== null) {
        store.enterBody(hit)
        return
    }

    // 否则 idle
    store.enterIdle()
}

export { tickHover }
```

#### 5.8.1 与原版的差异

- `state.active.locked` 派生量 → `store.isActiveLocked` computed,**不再写状态**
- 4 段 `if (state.phase === ...)` → `phaseHandlers` 字典分发,转移逻辑互斥更清晰
- 投影刷新只在 `activeEntity !== null` 时进行(原版每帧都尝试,内部再 null check)
- 不再导出可变 state,所有副作用通过 store action

#### 5.8.2 关于"理论不可达"的防御性守卫 —— 不变量为什么仍要兜底

5.7 与 5.8 中有 3 处守卫**理论上正常状态机流程下永远不会进入**:`enterBody` 的 `if (isActiveLocked.value) return`、`handleSticky` 的 `if (store.activeEntity === null)`、`tickHover` 的 `if (handler !== undefined)`。本节解释:为什么明知不可达,还要保留这三道守卫。

##### 1. 不变量的推导:理论上为什么不可达

state machine 写入 `activeEntity` 和 `phase` 的所有动作只在 4 个 action 里:

| Action | 对 `activeEntity` 的操作 | 对 `phase` 的操作 |
|---|---|---|
| `enterIdle()` | `= null` | `= 'idle'` |
| `enterBody(hitObject)` | `= hitObject`(非 null) | `= 'body'` |
| `enterSticky(nowMs)` | **不动** | `= 'sticky'` |
| `enterLabel()` | **不动** | `= 'label'` |

同时,`phase` 的写入值都取自 `HoverPhase` 枚举,而 `phaseHandlers` 字典的 key 恰好覆盖了 `HoverPhase` 的所有值——**三者一一对应**:

> `HoverPhase` 枚举值集合 = `phase` 的所有可能写入值 = `phaseHandlers` 字典的 key 集合 = `{ idle, body, sticky, label }`

由此可推三条不变量:

- **不变量 X**:`phase === 'sticky' ⟹ activeEntity !== null` —— `activeEntity = null` 仅由 enterIdle 触发,而 enterIdle 同步把 phase 设为 idle,绝不会留在 sticky
- **不变量 Y**:`isActiveLocked === true ⟹ phase === 'label'` —— isActiveLocked 在 label 阶段才可能为 true,而 tickHover 在 label 阶段不会触发到 enterBody
- **不变量 Z**:`phaseHandlers[store.phase] !== undefined` —— phase 的写入值始终落在 HoverPhase 枚举集合内,phaseHandlers 已覆盖该集合的全部元素

按这三条推导,以下三处守卫**永远不会被触发**:

| 位置 | 守卫表达式 | 对应不变量 |
|---|---|---|
| `enterBody()`(5.7) | `if (isActiveLocked.value) return` | 不变量 Y |
| `handleSticky()`(5.8) | `if (store.activeEntity === null) ...` | 不变量 X |
| `tickHover()`(5.8) | `if (handler !== undefined) ...` | 不变量 Z |

##### 2. 为什么还要写

是典型的**防御性编程**——防的不是"已知的执行路径",而是"未知 / 未来 / 破坏不变量的操作"。具体能想到的场景:

###### 场景 a:Pinia 暴露的 ref 是可写的,外部可以直接搞坏不变量

Pinia 的 Composition store 把 ref 直接暴露在 `store.xxx` 上,任何持有 store 的代码都可以这样写:

```js
// 某个 component 里、某个未来加的 watch 里、某个调试代码里
store.activeEntity = null   // ← 直接绕过 actions,合法且不会报错
```

这一写,`phase` 还是 `'sticky'`,`activeEntity` 已经被外部弄成了 null——下一帧 tickHover 跑到 handleSticky 时,这个分支就被触发了。

虽然当前代码库中没有这种调用,但 store 暴露的写入面是物理可达的,Pinia 不会拦截。这两道守卫等于在算法层补一道"外部绕过 action 也不会让我崩"的保险。

###### 场景 b:未来重构可能破坏不变量

假设某天加一个 action 叫 `clearActiveEntity()`,初衷是"在场景重置时清空当前激活的天体":

```js
function clearActiveEntity() {
    activeEntity.value = null
    // 忘了同步把 phase 也切到 idle
}
```

只要 `phase` 还停在 `sticky`,下一帧 handleSticky 就会拿到 `activeEntity === null`。这个守卫能让代码**不崩,优雅退化到 idle**,而不是在下游某个 `store.activeEntity.???` 之类的访问上抛 `Cannot read property 'xxx' of null`。

###### 场景 c:生命周期错配

页面正在卸载,SolarCanvas 的 `dispose()` 已经清理掉某些 Three.js 对象,但 animation loop 多跑了一帧(rAF 已经入队,还没有 cancel)。如果配合上"销毁逻辑顺手把 store 也清了"——`activeEntity = null` 又先于 phase 重置发生——这两道守卫也能挡住下游崩溃。

> **同一模式同样适用于不变量 Y 和 Z**:
> - 不变量 Y 被破坏的典型场景:外部直接写 `store.isLabelHover = true`,或未来加一个忘了配套切 phase 的 action
> - 不变量 Z 被破坏的典型场景:外部直接写 `store.phase = 'unknown'`(字符串绕过枚举),或扩展 HoverPhase 枚举但忘了同步 phaseHandlers
>
> 3 处守卫防御的本质都是同一类问题——"约定被破坏,但代码不应该崩溃"。

##### 3. 为什么不变量没有被"机制保证"

回到根本——上述 3 条不变量(X / Y / Z),目前都是**靠"大家都通过 actions 改 state"这条约定来保证的,不是靠类型系统或运行时机制强制的**。

要让它"机制保证",有两条路:

- **Options API 的 Pinia store**(只能通过 actions 写 state)—— 已因 JSDoc 兼容性放弃
- **不暴露 ref,只暴露 getters**(隐藏写入面)—— 现在的 Composition store 也没采用,因为 SolarLabel 模板需要直接读响应式字段

既然不变量"机制上没被强制",**算法层补一道运行时校验是合理的代价**——一次比较换取"以后任何破坏不变量的改动都不至于让 tickHover 崩"。

##### 4. 守卫的命名与文档化约定

为避免后续阅读时反复纠结"这个分支什么时候会进?",本工程约定:

- **凡是"理论不可达"的守卫,注释里必须写清楚两件事**:
  1. **理论不可达的推导**(基于哪些不变量得出不会触发)
  2. **保留的理由**(对应到 5.8.2 的场景 a / b / c 中的哪些)
- 注释末尾**引用 5.8.2**,避免在多个地方重复同一套解释

`enterBody`、`handleSticky`、`tickHover` 中这 3 处守卫的注释均已按此约定写好,后续若新增类似守卫,请保持同一风格。

##### 一句话总结

> **不变量靠约定保持,守卫为约定被破坏时兜底**。这两道守卫的代价是一次条件判断,换来的是"无论谁、怎么破坏 store 的状态,tickHover 至少不会崩,而是优雅退化到 idle"——这是处理高频帧循环时应有的稳健性。

改动 5 处:

1. 行星 + 太阳初始化完成后,**注册可拾取列表**:

   > `getAllPickableMeshes` 在 `planet/index.js` 已经存在,只需要 export(目前是模块内函数,没 export)。

2. 在模块顶层新增 `hoverStore` 状态机引用,与现有的 `rafId`、`controls` 同属"引擎生命周期内的模块级状态":
   ```js
   /**
    * @type {import('@/stores/hover.js').HoverStore|null} 当前引擎实例所持有的悬停状态机引用
    * */
   let hoverStore = null
   ```
   > `startAnimation` 是模块级函数(并非嵌套在 `initEngine` 内),没法通过闭包从 `initEngine` 的形参作用域访问状态机;放到模块级后,`startAnimation` 与 `dispose` 都能访问,卸载时也可以统一在 `dispose` 中释放。

3. `initEngine` 接收一个新形参 `store`,在函数体开头写入模块级 `hoverStore`(形参刻意不叫 `hoverStore` —— 同名形参会**遮蔽(shadow)**模块级变量,函数体内的 `hoverStore = ...` 就只是改形参,无法回写到模块级):
   ```js
   /**
    * ...
    * @param {HTMLDivElement} container 要挂载canvas的容器DOM
    * @param {import('@/stores/hover.js').HoverStore} store 定义状态机属性和行为的存储对象
    * @return {{canvas: HTMLCanvasElement, dispose: Function}} 引擎句柄:渲染所用的canvas DOM元素 + 销毁函数
    * */
   export async function initEngine(container, store) {
       hoverStore = store

       try {
           // ... 原有初始化逻辑 ...
       } catch (err) {
           // ... 原有异常分支 ...
       }

       return {
           canvas: renderer.domElement,
           dispose,
       }
   }
   ```
   > 返回 `{canvas, dispose}` 而非单一的 `dispose` —— 让 canvas 作为**显式产出物**交付给调用方,而不是让调用方从容器 DOM 中再 `querySelector('canvas')` 反查一次。`renderer.domElement` 本身就是 canvas,引擎内部一直握着这个引用;若对外只返回 `dispose`,SolarCanvas 就只能依赖"容器里第一个 canvas 就是渲染目标"这条没写出来的隐式约定来反推——边界显式比依赖 DOM 结构约定更稳。

4. 动画循环里调用 `tickHover`,并把 `shouldFreezeRevolution` 接到 `updatePlanets`。`startAnimation` 签名保持不变(由 `requestAnimationFrame` 调度,无法传参),直接读模块级 `hoverStore`:
   ```js
   import { tickHover } from '@/three/interaction/hover.js'

   function startAnimation() {
       rafId = requestAnimationFrame(startAnimation)
       const now = performance.now()

       setSkySphereAutoRotation()
       setSunAutoRotation()
       tickHover(now, hoverStore, camera, renderer.domElement)
       updatePlanets(!hoverStore.shouldFreezeRevolution)
       controls.update()
       renderBloomFrame()
   }
   ```

5. `dispose` 里把模块级 `hoverStore` 复位为 `null`,避免引擎卸载后仍持有失效的 store 引用:
   ```js
   function dispose() {
       // ... 原有清理逻辑(rafId / controls / bloom / renderer)...

       hoverStore = null
   }
   ```
   > 与现有的 `rafId = null`、`controls = null` 同一风格:**所有引擎生命周期内的模块级引用都在 `dispose` 里复位**,确保引擎"重新挂载"是一次干净的初始化。

### 5.10 `src/components/SolarCanvas.vue`(修改)

负责:
1. 把 hoverStore 传进 engine
2. **在 `renderer.domElement` 上**绑定 pointer 事件(不要绑 window)
3. 卸载时清理

```vue
<script setup>
import { useTemplateRef, onMounted, onBeforeUnmount } from 'vue'
import { useHoverStore } from '@/stores/hover.js'
import { initEngine } from '@/three/engine.js'
import { getNDCCoordinate, setLeaveCoordinate } from '@/three/lib/pointer.js'

/**
 * @type {Readonly<import('vue').ShallowRef<HTMLDivElement|null>>} 模板引用,指向canvas的容器DOM元素(.solar-canvas)
 * */
const containerRef = useTemplateRef('container')

/**
 * @type {import('@/stores/hover.js').HoverStore} 悬停状态机的store实例
 * */
const hoverStore = useHoverStore()

/**
 * @type {Function|null} 引擎的销毁函数,由initEngine返回,组件卸载时调用
 * */
let dispose = null

/**
 * @type {HTMLCanvasElement|null} 引擎渲染所用的canvas DOM元素,由initEngine的返回值提供
 * */
let canvas = null

/**
 * @type {Boolean} 标识当前组件是否已被卸载.用于在initEngine异步初始化期间组件被卸载的竞态下,
 *                 让onMounted回调在await返回后能感知卸载已发生,立即释放刚拿到的引擎实例(详见末尾说明)
 * */
let isUnmounted = false

/**
 * 本函数为canvas的pointermove事件回调:
 *     1. 标记指针在canvas内
 *     2. 标记"指针已经至少触发过一次pointermove"(供射线检测做初次有效性判定)
 *     3. 计算并写入指针的NDC坐标(供射线检测使用)
 *     4. 写入指针的屏幕像素坐标(供label滞回判定使用)
 * @param {PointerEvent} event pointermove事件对象
 * */
function onPointerMove(event) {
    hoverStore.setPointerInCanvas(true)
    hoverStore.markPointerMoved()
    const ndc = hoverStore.pointer.ndcCoordinate
    getNDCCoordinate(event.clientX, event.clientY, canvas, ndc)
    hoverStore.setPointerScreen(event.clientX, event.clientY)
}

/**
 * 本函数为canvas的pointerenter事件回调:
 *     1. 标记指针进入canvas
 * */
function onPointerEnter() {
    hoverStore.setPointerInCanvas(true)
}

/**
 * 本函数为canvas的pointerleave事件回调:
 *     1. 标记指针离开canvas
 *     2. 将NDC坐标设置为越界哨兵值(避免射线检测在指针离开后仍按"最后一个有效NDC坐标"持续投射)
 * */
function onPointerLeave() {
    hoverStore.setPointerInCanvas(false)
    setLeaveCoordinate(hoverStore.pointer.ndcCoordinate)
}

/**
 * 本组件挂载完成后:
 *     1. 初始化3D引擎,并把状态机store传入(用于tickHover的状态读写以及updatePlanets的暂停联动)
 *     2. await期间组件可能已被卸载——若是,立即销毁刚拿到的引擎实例并返回(避免遗漏卸载)
 *     3. 保存引擎返回的销毁函数与canvas DOM元素引用(由initEngine显式返回,无需DOM查询)
 *     4. 在canvas上绑定pointer相关事件(绑canvas而非window,确保事件只在canvas区域内触发)
 * */
onMounted(async () => {
    const engine = await initEngine(containerRef.value, hoverStore)
    if (isUnmounted) {
        engine.dispose()
        return
    }
    dispose = engine.dispose
    canvas = engine.canvas
    canvas.addEventListener('pointermove', onPointerMove)
    canvas.addEventListener('pointerenter', onPointerEnter)
    canvas.addEventListener('pointerleave', onPointerLeave)
})

/**
 * 本组件卸载前:
 *     1. 置 isUnmounted = true,通知"仍在await initEngine"中的onMounted回调:卸载已发生
 *     2. 移除canvas上的pointer相关事件监听
 *     3. 调用引擎的销毁函数(释放渲染器/控制器/后期处理管线/模块级状态机引用)
 * */
onBeforeUnmount(() => {
    isUnmounted = true
    if (canvas !== null) {
        canvas.removeEventListener('pointermove', onPointerMove)
        canvas.removeEventListener('pointerenter', onPointerEnter)
        canvas.removeEventListener('pointerleave', onPointerLeave)
    }
    dispose?.()
})
</script>

<template>
    <div ref="container" class="solar-canvas"></div>
</template>
```

> 不绑定 `pointerdown`/`pointerup`/click —— 那些是阶段 9(点击聚焦)的事。

#### 5.10.1 关于 `isUnmounted` —— 防御 async 初始化与 unmount 的竞态

`initEngine` 是 `async` 的,内部 `await` 了多个异步初始化(场景环境、天空球、太阳、行星等)。意味着 `onMounted` 回调在 `await initEngine(...)` 处会挂起、让出执行权。若组件恰好在此期间被卸载(路由跳走、父组件 `v-if` 切走),会出现如下时序:

```
t0: onMounted 进入 → await initEngine(...) 挂起
    - 此时 dispose 仍为 null
t1: 组件卸载 → onBeforeUnmount 触发
    - dispose 仍为 null,dispose?.() 是空操作
    - canvas 仍为 null,事件解绑分支也是空操作
t2: 微任务调度回 onMounted → await resolve,得到 engine 句柄(含 dispose 与 canvas)
    - 引擎内部资源已分配:渲染器挂到了 DOM、rAF 已经启动、模块级 hoverStore 已赋值……
    - 若 onMounted 继续往下走 → 卸载已结束,资源永远不会再被清理
```

`isUnmounted` 把这个缝隙补上:`onBeforeUnmount` 立即置 `true`,`onMounted` 在 `await` 之后第一时间检查它——若发现"卸载已发生",**立即调用 `engine.dispose()` 并 `return`**,后续对模块级 `dispose` / `canvas` 的赋值与事件绑定也都被跳过。否则,模块级 `dispose` 仍为 `null`,`onBeforeUnmount` 中的 `dispose?.()` 是空操作,引擎里的 rAF、渲染器、模块级 `hoverStore` 也将永远不会再被清理。

> 此处的关键是"诚实地承认 `onMounted(async () => ...)` 的回调不是原子的":只要其中存在 `await`,就一定要为 await 之后的代码考虑"组件是否还活着"。`isUnmounted` 标量是这个语义最直白的表达,比依赖更复杂的取消 token / AbortController 更轻。

### 5.11 `src/components/SolarLabel.vue`(修改)

负责:
1. 根据 `shouldShowLabel` 控制自身显隐(`v-show` 或 opacity 动画;opacity 方案需要配套 `.solar-label.is-visible` 的 CSS 契约,详见 5.11.2)
2. 在自身根元素上监听 `pointerenter`/`pointerleave`,写 `isLabelHover` 到 store
3. **每次自身位置/尺寸变化后,把 `getBoundingClientRect()` 写回 store**(让 `tickHover` 知道 label 在哪里,以判定 isNearLabel)

```vue
<script setup>
import { computed, watch, nextTick, useTemplateRef } from 'vue'
import { useHoverStore } from '@/stores/hover.js'

/**
 * @type {Readonly<import('vue').ShallowRef<HTMLDivElement|null>>} 模板引用,指向 .solar-label 容器 DOM
 * */
const containerRef = useTemplateRef('container')

/**
 * @type {import('@/stores/hover.js').HoverStore} 悬停状态机的 store 实例
 * */
const hoverStore = useHoverStore()

/**
 * @type {import('vue').ComputedRef<{left: String, top: String}>} label 的 CSS 定位样式
 *      Tips: 暂用 activeProjection 的中心点作为占位实现;阶段 9 接 calcOffset 后只改本 computed 内部逻辑
 * */
const positionStyle = computed(() => {
    const c = hoverStore.activeProjection.centerPx
    return { left: `${c.x}px`, top: `${c.y}px` }
})

/**
 * 本函数为容器 div 的 pointerenter 事件回调:
 *     1. 标记鼠标进入 label(写 isLabelHover = true)
 * Tips: isLabelHover 被 isActiveLocked 派生量读取,使状态机在 label 阶段锁定 activeEntity
 * */
function onPointerEnter() {
    hoverStore.setLabelHover(true)
}

/**
 * 本函数为容器 div 的 pointerleave 事件回调:
 *     1. 标记鼠标离开 label(写 isLabelHover = false)
 * */
function onPointerLeave() {
    hoverStore.setLabelHover(false)
}

/**
 * 显隐状态或定位变化后,把容器自身的 getBoundingClientRect() 写回 store,供 tickHover 做 isNearLabel 滞回判定:
 *     - shouldShowLabel 变化(idle ↔ 非 idle):决定是否上报 rect
 *     - positionStyle.left / top 变化(activeEntity 屏幕投影位置变化):rect 需要重新拍照
 *     - immediate: true:初次挂载时也跑一次,保证 store.labelRect 与当前渲染状态同步

 * */
watch(
    () => [hoverStore.shouldShowLabel, positionStyle.value.left, positionStyle.value.top],
    async () => {
        await nextTick()
        if (hoverStore.shouldShowLabel && containerRef.value !== null) {
            hoverStore.setLabelRect(containerRef.value.getBoundingClientRect())
        } else {
            hoverStore.setLabelRect(null)
        }
    },
    { immediate: true },

</script>

<template>
    <div
        ref="container"
        class="solar-label"
        :style="positionStyle"
        :class="{ 'is-visible': hoverStore.shouldShowLabel }"
        @pointerenter="onPointerEnter"
        @pointerleave="onPointerLeave"
    >
        <Shape />
        <OuterDecorLayer />
        <ContentLayer />
    </div>
</template>
```

#### 5.11.1 为什么 isNearLabel 判定放在 tickHover 而不是 SolarLabel

直觉上,"鼠标是否靠近 label"在语义上是关于 label 这个组件的事,应该写在 SolarLabel 里——例如一个监听 `pointer.screenPx` 与 `labelRect` 的 watch。展开后会发现这条路径有两个硬伤,所以选择把判定放到 tickHover。

##### 1. `pointer.screenPx` 不是响应式数据

`src/stores/hover.js` 里的 `pointer` 字段是裸 JS 对象(既不是 `ref()`,也不是 `reactive()`),这是**有意为之**——它每帧高频更新、不被任何模板直接读取,响应式只会浪费性能(参见 hover.js 的 PART3 注释)。

Vue 的 `watch` 依赖响应式订阅,getter `() => [hoverStore.pointer.screenPx.x, ...]` 里读 `screenPx.x`/`.y` 只在初次收集依赖时取一次值;后续这两个字段被 `setPointerScreen` 改写时,Vue 收不到任何通知,watch 不会重跑——**写出来的 watch 看似是响应式订阅,实际只是"初次取值的快照"**。

##### 2. 判定有两个独立触发源,SolarLabel 的 watch 只能感知一个

`isNearLabel` 真正依赖的状态变化有两条线:

| 触发源 | SolarLabel 的 watch 能感知吗? |
|---|---|
| 鼠标移动 → `pointer.screenPx` 变化 | ❌(pointer 非响应式) |
| **相机移动**(OrbitControls 拖拽)→ `activeProjection` 变化 → label 重新定位 → `labelRect` 变化 | ✅(labelRect 是 shallowRef) |

即便修补了第 1 条(把 pointer 升级成响应式),依然只覆盖"鼠标动"一支;**"相机动 / 鼠标不动"这一支需要在每帧重新拍照后才能看到**——典型例子:用户停住鼠标拖动相机,label 跟着移动到鼠标旁,这时鼠标不动、pointermove 不触发,SolarLabel 的 watch 漏判。

##### 3. 为什么 tickHover 天然合适

tickHover 每帧固定执行一次,这一帧内三个输入都是新鲜的:

- `pointer.screenPx`:SolarCanvas 在 pointermove 里已经实时写入,直接读裸字段即可(无需响应式)
- `activeProjection`:tickHover 自己刚刚刷新过(`store.setActiveProjection(...)`)
- `labelRect`:SolarLabel 的 rect 上报 watch 在响应 `positionStyle` 变化后已经写入 store

把 `isNearRect` / `isFarRect` 的滞回判定加进 tickHover,**自然同时覆盖两个触发源**,且 pointer 字段保持非响应式,零代价。

实现见 5.8 tickHover 的步骤 3——**位置在阶段分发(`phaseHandlers[store.phase]`)之前**:各 handler 读取的 `isActiveLocked` 派生自 `isNearLabel`(`isLabelHover || isNearLabel`),顺序错了会拿到上一帧的滞后值,出现"鼠标已离开,label 仍锁定"之类的视觉延迟。

##### 4. 最终的组件职责划分

| 组件 / 模块 | 职责 |
|---|---|
| SolarCanvas | 把瞬时输入翻译成 store 字段(`setPointerNDC` / `setPointerScreen` / `setPointerInCanvas` / `markPointerMoved`)|
| SolarLabel | ① `pointerenter` / `pointerleave` 写 `isLabelHover`;② 上报自身 `getBoundingClientRect()` 给 store;③ 按 store 的状态渲染 |
| tickHover | 每帧拍照、跑状态机,**包括所有距离判定**(投影边缘距离 + label 矩形滞回) |

距离判定全部集中在 tickHover,符合 5.7.2 的「副作用在边界、纯逻辑在中间」——DOM 事件(SolarCanvas、SolarLabel)只做单向数据写入,几何判定与状态推进集中在 tickHover。

#### 5.11.2 `.is-visible` 的 CSS 契约 —— 显隐与 pointer-events 联动

5.11 模板里的 `:class="{ 'is-visible': hoverStore.shouldShowLabel }"` 不是孤立绑定——它依赖一条**未写在 `<script>` 里**的 CSS 契约:由 `.solar-label.is-visible` 规则把"默认隐藏态"翻转为"可见态"。最小骨架:

```css
.solar-label {
    /* 默认隐藏态 */
    opacity: 0;
    visibility: hidden;
    pointer-events: none;
    transition:
        opacity 0.5s linear,
        visibility 0s linear 0.5s;     /* visibility 在 opacity 跑完后才切 */
}

.solar-label.is-visible {
    /* 可见态 */
    opacity: 1;
    visibility: visible;
    pointer-events: auto;
    transition:
        opacity 0.5s linear,
        visibility 0s linear 0s;       /* 显示时立刻可见,再淡入 */
}
```

三条属性各自承担一项责任:

| 属性 | 默认 | `.is-visible` | 作用 |
|---|---|---|---|
| `opacity` | `0` | `1` | 配合 transition 形成淡入 / 淡出 |
| `visibility` | `hidden` | `visible` | 控制元素是否参与渲染;离散属性,需要差异化 transition |
| `pointer-events` | `none` | `auto` | **关键**:控制元素是否接收鼠标事件 |

##### 为什么 `pointer-events` 必须翻

默认 `pointer-events: none` 让 DOM 在事件分发阶段就把该元素当透明——`@pointerenter` / `@pointerleave` 整条事件链不会触发。若忘了在 `.is-visible` 里翻回 `auto`,会出现:

- 视觉上 label 显示了(`opacity = 1`)
- 鼠标移到 label 上方 → `onPointerEnter` 不触发 → `isLabelHover` 永远为 false
- 状态机的 label 阶段**只能靠 `isNearLabel`**(tickHover 的几何判定)进入,`isLabelHover` 这条路径整条失效

这是阶段 8 联调时容易"看上去好像跑通了"、实际有半条线没接通的典型陷阱。

##### 为什么 `visibility` 的 transition 要分两段

`visibility` 是离散属性,直接 `transition: visibility 0.5s linear` 会让浏览器在过渡中点附近"突变",时机不可控。把默认态与 `.is-visible` 态的 transition 写成差异化:

- **淡出**(`.is-visible` 被移除):opacity 在 0.5s 内渐变到 0 期间,visibility 仍为 `visible`(让元素继续参与渲染、维持鼠标响应);0.5s 后 visibility 才切到 `hidden`
- **淡入**(`.is-visible` 被加上):visibility 立即变为 `visible` → opacity 在 0.5s 内渐变到 1

如果两态用同一条 transition,淡出时元素会在 opacity 还没跑完前就 `visibility: hidden`,鼠标停留时会有"label 突然消失"的视觉跳跃。

## 7. 状态机转移规则

| 当前 phase | 触发条件 | 目标 phase | 备注 |
| --- | --- | --- | --- |
| idle | `pickHoveredBody !== null` | body | |
| body | `isActiveLocked === true` | label | 优先级最高(label 区域可与天体投影重叠) |
| body | `pickHoveredBody !== null` | body(若不同天体则切换) | 同一天体保持当前态 |
| body | 进入粘滞环(`0 < dist < enterEdge`) | sticky | |
| body | 否则 | idle | |
| sticky | `isActiveLocked === true` | label | |
| sticky | `pickHoveredBody !== null` | body | |
| sticky | `elapsed >= expireMs` | idle | 超时强制退出 |
| sticky | `elapsed >= minHoldMs && dist >= exitEdge` | idle | 距离退出 |
| label | `isActiveLocked === true` | label | 保持 |
| label | `pickHoveredBody !== null` | body | |
| label | 否则 | idle | |

### 7.1 sticky 的最短保留(`minHoldMs`)的作用

这是**防止鼠标在"粘滞环"和"label 附近区域"之间的过渡缝隙里把 label 抖掉**。原文档 `/doc/minHoldMs的作用.png` 描述了这一物理几何关系。在重构时这个语义保留不变。

### 7.2 hasEverMoved 防御

页面初次加载时,鼠标默认在 (0,0)(浏览器约定),`pointer.ndcCoordinate` 也对应到了视口左上角附近。如果不防御,刚加载就可能 raycast 到天体,出现 "用户没动鼠标但 label 自己冒出来了" 的违和感。

`tickHover` 第一行:
```js
if (!store.pointer.hasEverMoved) {
    if (store.phase !== hoverPhase.idle) store.enterIdle()
    return
}
```

`hasEverMoved` 在 `pointermove` 事件首次触发时由 `markPointerMoved` 置为 true,**不再回退**。

## 10. 风险与备注

### 10.1 `pointer.screenPx` 不是响应式 — 由 tickHover 主动消费

如 5.11.1 所述,把 `isNearLabel` 判定挪到 `tickHover` 后,`pointer.screenPx` 完全不需要响应式,store 中保持普通对象即可。**注意:**模板里**不要**直接 bind 这个非响应式字段(否则不会刷新)。如果将来确实需要在模板里显示鼠标坐标,**那时候**再升级为 ref。

### 10.2 `activeEntity` 用 shallowRef

不要用 `ref()` 包 `THREE.Object3D`。Vue 3 的 reactive proxy 会递归代理 three.js 内部所有 mesh / geometry / material,既无意义又会触发 three 内部状态变更时的级联重新渲染。`shallowRef` 只追踪引用本身的变更,正合需求。

### 10.3 投影刷新 vs 公转动画的时序

每帧顺序:
1. `setSkySphereAutoRotation`、`setSunAutoRotation` —— 自转更新
2. `tickHover` —— 读取上一帧的位置 + 推进状态机 + **重算 activeProjection**
3. `updatePlanets(!shouldFreezeRevolution)` —— 行星公转更新(**仅当未冻结时**)
4. `controls.update`
5. `renderBloomFrame`

注意 **tickHover 在 updatePlanets 之前**:要先用上一帧的位置算投影,然后再公转。否则鼠标已经在 sticky 状态了,行星却又走了一步,投影圆和鼠标的相对位置可能突变。原项目就是这个顺序,迁移时保留。

### 10.4 raycaster 的 pickables 一次注册 vs 动态注册

当前设计是 `setPickables(meshes)` 一次性注册。如果未来要支持"动态显示/隐藏某颗行星"这种功能,需要在切换时重新调 `setPickables`。本次迁移不做这一步,保持简单。

### 10.5 阶段 9 的衔接点

`focus.js` 的迁移依赖本阶段两件事:
1. **`hoverStore.activeEntity`** —— 点击聚焦时,需要从 store 读出当前激活的天体
2. **`hoverStore.enterIdle()`** —— 聚焦时强制清空 hover 状态,避免聚焦动画期间 label 还在闪

只要 store 这两个 API 稳定,阶段 9 就只需要新增 `focus` 相关的逻辑和 `pointerdown`/`pointerup` 事件,不需要再动 hover 这一块。

### 10.6 关于 `pointer.inCanvas`

字段保留,但在新版 `tickHover` 里没有直接消费(因为 `hasEverMoved` + `pointerleave` 时 `setLeaveCoordinate(9999, 9999)` 已经隐含表达了"不在画布上 → raycaster 拿不到任何东西")。如果未来要做 "鼠标离开画布时立即清空状态" 的优化,再用上这个字段。
